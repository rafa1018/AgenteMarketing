# WhatsApp Business Platform (Cloud API): capacidades, límites, precios y políticas

Fecha de verificación: 2026-09-21

## Resumen ejecutivo (5-10 viñetas con lo que más impacta el diseño)

- La **On-Premises API está muerta**: la última versión soportada caducó el 23 de octubre de 2025; desde esa fecha ya no se entregan mensajes enviados por esa vía. El diseño **debe** usar Cloud API (alojada por Meta) sin discusión (https://developers.facebook.com/docs/whatsapp/on-premises/sunset).
- **Coexistence** (mismo número en la app WhatsApp Business del celular + Cloud API a la vez) existe oficialmente vía Embedded Signup y, según fuentes de la propia Meta y agregadores del ecosistema, para 2026 su disponibilidad ya es prácticamente mundial (incluida Latinoamérica); no se encontró una lista oficial y explícita de países vigente en `developers.facebook.com` al momento de verificar, por lo que la cobertura exacta en Colombia hoy queda **NO VERIFICADO** y debe confirmarse en el flujo real de Embedded Signup antes de decidir la arquitectura del número.
- El modelo de precios cambió radicalmente: desde el **1 de julio de 2025** Meta cobra **por mensaje de plantilla entregado**, no por "conversación" de 24 horas. Los mensajes de servicio (respuesta libre dentro de la ventana de 24 h) siguen siendo gratis (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Los mensajes iniciados por la empresa (incluido el "menú matutino proactivo" al dueño) **requieren plantilla aprobada** (Marketing/Utility/Authentication) si el dueño no ha escrito en las últimas 24 h; eso implica costo por mensaje de plantilla salvo que el dueño escriba primero cada día.
- Existen **límites de mensajería por niveles** (250 → 2,000 → 10,000 → 100,000 → ilimitado, calculados ahora a nivel de *Business Portfolio*, no por número) y un **límite por-usuario de plantillas de marketing** (dinámico, no publicado como cifra fija) que puede bloquear el envío con el error 131049 (https://developers.facebook.com/docs/whatsapp/messaging-limits/).
- **No existe** API para publicar Estados/Stories de WhatsApp. Los "grupos" tuvieron una **Groups API oficial muy reciente (documentada en 2026)**, pero exige que la cuenta sea **Official Business Account (OBA)** y no aplica a números en la app WhatsApp Business ni en coexistencia — no es un sustituto práctico de "difusión estilo app" para este proyecto.
- No existe una "lista de difusión" real en la API: cualquier envío masivo es, técnicamente, **N envíos individuales** (uno por destinatario), sujeto a límites de nivel y a plantillas.
- **Catálogo y carrito sí existen** (product/catalog/cart messages), pero dependen de un catálogo de Meta Commerce Manager — es una capacidad de fase posterior, no del MVP.
- El número de prueba automático de Meta permite enviar a un máximo de **5 destinatarios verificados**; sirve solo para desarrollo, no para producción con el dueño ni con clientes reales.
- n8n **sí** tiene nodos maduros: `WhatsApp Business Cloud` (mensajes, plantillas, media, y "Send and Wait for Response") y `WhatsApp Trigger`; también existe soporte del objeto `whatsapp_business_account` en el nodo `Facebook Trigger`, aunque n8n mismo recomienda el `WhatsApp Trigger` dedicado.

## Hechos verificados (cada viñeta termina con la URL fuente entre paréntesis)

- La versión final del cliente On-Premises expiró el 23 de octubre de 2025; desde esa fecha los mensajes enviados por números aún registrados en On-Premises no se entregan (https://developers.facebook.com/docs/whatsapp/on-premises/sunset).
- Desde el 1 de julio de 2024 los números de teléfono comerciales solo pueden registrarse para uso con Cloud API (no con On-Premises) (https://developers.facebook.com/docs/whatsapp/on-premises/sunset).
- Cloud API está alojada por Meta (no requiere que la empresa mantenga servidores propios) y soporta throughput de hasta 1,000 mensajes/segundo (https://developers.facebook.com/docs/whatsapp/on-premises/sunset).
- El costo de usar la API en sí (aparte de los mensajes de plantilla) no tiene una cuota de suscripción propia documentada; el cobro es por mensaje entregado según categoría, no por "acceso a la API" (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- **Coexistence** permite usar la app WhatsApp Business del celular y la Cloud API al mismo tiempo sobre el mismo número, sincronizando mensajes en tiempo real entre ambos vía webhooks, mediante el flujo de Embedded Signup para usuarios de la app WhatsApp Business (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- El onboarding de coexistencia exige la app WhatsApp Business en versión **2.24.17 o superior** en el celular del dueño, y que el sistema integrador ya sea **Solution Partner o Tech Provider** con conocimiento de Cloud API (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- En coexistencia, el historial de chats se sincroniza solo hasta **180 días** hacia atrás, y los archivos multimedia solo si fueron enviados en los últimos **14 días**; los chats de **grupo no se sincronizan** (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- Tras habilitar coexistencia hay una ventana de **24 horas** para completar la sincronización del historial, o el número debe ser "offboarded" (desconectado) (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- El throughput de un número en coexistencia (app + Cloud API simultáneos) está fijado en **20 mensajes por segundo** (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- En coexistencia, los mensajes enviados desde la app WhatsApp Business del celular siguen siendo gratis; los enviados vía Cloud API se facturan según el pricing de Cloud API (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- Funciones deshabilitadas cuando el número está en coexistencia: mensajes que desaparecen, "ver una vez", ubicación en vivo, y listas de difusión de la app (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users).
- El número de teléfono de prueba (test number) que Meta genera automáticamente al configurar Cloud API permite enviar a hasta **5 números destinatarios** agregados manualmente como "allowlist"; fuera de esos 5, no entrega mensajes (https://developers.facebook.com/documentation/business-messaging/whatsapp/get-started — confirmado además por comunidad de desarrolladores de Meta).
- Desde el **1 de julio de 2025** el modelo de precios pasó de "por conversación" a **"por mensaje de plantilla entregado"**; solo se cobra cuando el mensaje de plantilla es entregado (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Las categorías de plantilla son **Marketing, Utility y Authentication**; los mensajes de Utility y Authentication son gratis si se envían **dentro** de una ventana de servicio activa (customer service window), y se cobran si se envían **fuera** de ella; los mensajes que no son de plantilla (respuestas libres) son siempre gratis dentro de la ventana de servicio (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Colombia aparece explícitamente en la documentación de pricing de Meta como mercado con cambio de tarifas: "Effective October 1, 2025 ... Colombia – Higher utility and authentication rates" (tarifas más altas de utility y authentication desde esa fecha) (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Meta actualiza el rate card trimestralmente (1 de enero, abril, julio, octubre) (https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Los límites de mensajería (messaging limits) se definen como el número máximo de números de WhatsApp únicos a los que la empresa puede entregar mensajes **fuera de una ventana de servicio**, en una ventana móvil de 24 horas, y se calculan **a nivel de Business Portfolio**, compartidos entre todos los números de teléfono de ese portafolio (https://developers.facebook.com/docs/whatsapp/messaging-limits/).
- Los portafolios nuevos empiezan en el nivel **250**; para subir a **2,000** se debe cumplir una de estas rutas: verificar el negocio (Business Verification), que un partner lo verifique, o enviar 2,000 mensajes entregados fuera de ventana de servicio a números únicos en 30 días con plantillas de alta calidad (https://developers.facebook.com/docs/whatsapp/messaging-limits/).
- Por encima de 2,000, el escalamiento a 10,000 → 100,000 → ilimitado es **automático** si se mantiene calidad alta en todos los números/plantillas y se usa al menos la mitad del límite vigente en los últimos 7 días; los incrementos pueden ocurrir dentro de 6 horas (https://developers.facebook.com/docs/whatsapp/messaging-limits/).
- El campo `messaging_limit_tier` está deprecado; se debe solicitar `whatsapp_business_manager_messaging_limit` (https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits — vía changelog).
- Existe un **límite por-usuario de mensajes de plantilla de marketing**: WhatsApp puede limitar cuántas plantillas de marketing recibe un mismo usuario desde cualquier negocio en un período dado; es dinámico (no una cifra fija publicada), basado en la tasa de lectura reciente del usuario y cuántos mensajes tiene en su bandeja; el error correspondiente es el **código 131049** en el webhook de estado (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/marketing-templates/per-user-limits).
- Ese límite por-usuario **no aplica** a mensajes en el European Economic Area, Reino Unido, Japón o Corea del Sur, y las plantillas de marketing **no pueden enviarse** a números de EE.UU. (https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/marketing-templates/per-user-limits).
- La calificación de calidad (quality rating) de un número es Verde/Amarillo/Rojo, basada en señales de los últimos 7 días (bloqueos, reportes, motivos de bloqueo); si baja a Rojo persistente el número puede quedar "Flagged" y, si no mejora en 7 días, "Paused" (pausado, no puede enviar mensajes iniciados por la empresa hasta resolver) (fuente oficial de Meta referenciada por agregadores del ecosistema; el mecanismo general de calidad está documentado en developers.facebook.com bajo phone number quality rating — **el detalle textual exacto de "Flagged/Paused" se tomó de fuentes secundarias, ver sección de no verificados**).
- **No existe** función de API para publicar Estados (Status/Stories) de WhatsApp; esa función es exclusiva de la app y no está expuesta por Cloud API (confirmado por ausencia total de endpoint en la referencia oficial de Meta para Messages/Media; no hay `POST .../status` en https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages).
- **Sí existe** una **Groups API** oficial y documentada por Meta (`developers.facebook.com/documentation/business-messaging/whatsapp/groups`), pero exige que el negocio tenga status de **Official Business Account (OBA)**; **no está disponible** para números en la app WhatsApp Business ni para números incorporados a "Multi-solution Conversations"; grupos de hasta **8 participantes**, hasta **10,000 grupos por número de negocio**, solo un negocio Cloud API por grupo; soporta texto, media y plantillas de texto/media; **no soporta** llamadas, mensajes que desaparecen, "ver una vez", authentication, comercio ni mensajes interactivos; se factura con el mismo modelo per-message (https://developers.facebook.com/documentation/business-messaging/whatsapp/groups).
- Las "listas de difusión" tipo app **no existen** como función nativa de la API: cualquier envío a múltiples destinatarios se implementa como **múltiples llamadas individuales** al endpoint de mensajes, una por destinatario (deducido de la referencia de la API de mensajes, que solo acepta un `to` por request: https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages).
- Los mensajes de catálogo/producto (single product, multi-product, catalog message) **sí existen**; el catálogo de productos se administra vía Commerce Manager o Commerce API, y el carrito ("cart") permite que el cliente agregue varios productos y envíe un pedido único por chat (https://developers.facebook.com/documentation/business-messaging/whatsapp/catalogs/catalogs-overview/).
- El endpoint de envío de mensajes es `POST /{Phone-Number-ID}/messages`; soporta tipos text, image, audio, video, document, sticker, location, reaction, contacts, interactive (buttons, list, product, product_list, flows, catalog) y template (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages).
- Los botones de respuesta rápida (`interactive.button`) admiten **máximo 3 botones**; los mensajes de lista (`interactive.list`) admiten hasta 10 secciones con **hasta 10 filas en total** sumando todas las secciones (https://developers.facebook.com/docs/whatsapp/cloud-api/messages/interactive-reply-buttons-messages ; https://developers.facebook.com/docs/whatsapp/cloud-api/messages/interactive-list-messages/).
- Los botones de "Call-to-Action URL" (`interactive.cta_url`) permiten mapear una URL a un botón sin exponer la URL cruda en el cuerpo del mensaje (https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-cta-url-messages).
- Los mensajes de tipo **Flows** permiten experiencias estructuradas (formularios, reservas, catálogos) dentro del chat, usando `flow_id` y `flow_cta` (https://developers.facebook.com/documentation/business-messaging/whatsapp/messages — referencia de interactive messages).
- Subida de media: `POST /{Phone-Number-ID}/media`; obtención de URL: `GET /{Media-ID}` (opcionalmente con `phone_number_id`); la **URL de descarga expira a los 5 minutos** y debe volver a solicitarse; los media subidos vía API se retienen 30 días, y los media recibidos por webhook están disponibles para descarga por 7 días (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media — con matices de expiración recopilados de la referencia oficial).
- Límites de tamaño de media: audio 16 MB, documentos 100 MB, imágenes 5 MB, stickers 100–500 KB, video 16 MB (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media).
- Marcar un mensaje entrante como leído (`status: "read"`) se hace con `POST /{Phone-Number-ID}/messages` usando el `message_id`; se puede combinar con un indicador de "escribiendo" (`typing_indicator`) que se descarta automáticamente al responder o a los **25 segundos**, lo que ocurra primero; solo se pueden marcar como leídos mensajes recibidos hasta 30 días atrás (https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/mark-message-as-read).
- La creación de plantillas se hace vía `POST /{WABA-ID}/message_templates`; las plantillas pasan por un flujo de revisión con estados (aprobada/rechazada/pendiente); las categorías oficiales son Marketing, Utility y Authentication (confirmado por la referencia de pricing y templates de Meta: https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing).
- Los webhooks de WhatsApp requieren una URL pública HTTPS de tu servidor; el registro exige superar un **handshake GET** con `hub.mode=subscribe`, `hub.verify_token` y `hub.challenge`, respondiendo 200 con el valor crudo del challenge (fuente oficial y confirmado por múltiples guías técnicas: https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview).
- Cada notificación de evento POST llega firmada con el header **`X-Hub-Signature-256`** (HMAC-SHA256 sobre el cuerpo crudo, usando el App Secret) que debe verificarse antes de procesar el payload (documentado en el flujo estándar de Webhooks de la plataforma de Meta; ver overview oficial arriba).
- Meta **reenvía (retries)** notificaciones de webhook a todas las apps suscritas, lo que **puede producir duplicados**; el consumidor debe deduplicar por `message.id` / `status.id` (https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview).
- Los campos de webhook relevantes incluyen `messages` (mensajes entrantes y actualizaciones de estado salientes), `message_template_status_update`, y campos de cuenta como `account_alerts`, `account_review_update`, `account_update` (https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/overview).
- Dentro del campo `messages`, los mensajes entrantes viven en `entry[].changes[].value.messages[]` y los recibos de entrega en `value.statuses[]` (con estados `sent`, `delivered`, `read`, `failed`); cada mensaje saliente puede generar hasta 3 callbacks (sent/delivered/read) (documentado en la referencia de webhooks de Meta, consistente con guías técnicas oficiales y de socios).
- En **modo Development** (app no revisada), algunos webhooks no se envían y solo se puede interactuar con números/destinatarios de prueba (fuente oficial de comportamiento de apps de Meta en modo desarrollo; documentado de forma consistente en la guía de configuración de Cloud API).
- Los permisos relevantes son **`whatsapp_business_management`** (acceso a la configuración de la WABA y plantillas) y **`whatsapp_business_messaging`** (acceso a la configuración del número de teléfono y envío/recepción de mensajes); ambos requieren **App Review** y "Advanced Access" antes de poder operar con clientes/cuentas reales (https://developers.facebook.com/documentation/business-messaging/whatsapp/permissions).
- La **WABA (WhatsApp Business Account)** vive dentro de un **Business Portfolio** (antes "Business Manager"); el **System User token** es el mecanismo recomendado para automatizaciones server-to-server como n8n, en lugar de un token de usuario personal (https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens/).
- **Embedded Signup** es el flujo recomendado para que un cliente (o el propio dueño) conecte su WABA/número sin pasar manualmente por el dashboard completo de Meta; requiere que la app del integrador tenga los permisos `whatsapp_business_management` y `whatsapp_business_messaging` aprobados (https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/overview/).
- El **Official Business Account (OBA)**, distinguido con la marca de verificación azul, es **opcional** y separado de la verificación de negocio básica: se solicita aparte y hoy Meta exige que la solicitud la presente un Business Solution Provider (fuente agregada de terceros basada en documentación de Meta Business Help Center; **marcar como parcialmente NO VERIFICADO** el requisito de "solo vía Solution Provider").
- El opt-in es obligatorio antes de enviar cualquier mensaje iniciado por la empresa; debe indicar claramente el nombre del negocio y el tipo de mensajes, y permitir opción de exclusión; desde una actualización de política de noviembre de 2024, el opt-in ya no necesita mencionar específicamente "WhatsApp" como canal —un opt-in general de marketing/servicio recogido en cualquier canal es válido— (https://developers.facebook.com/documentation/business-messaging/whatsapp/getting-opt-in).
- n8n tiene un nodo dedicado **WhatsApp Business Cloud** con operaciones de mensaje (Send, Send Template, **Send and Wait for Response** con modos Approval / Free Text / Custom Form) y de media (Upload, Download, Delete) (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.whatsapp).
- n8n tiene un nodo dedicado **WhatsApp Trigger** para eventos de mensaje, cuenta y número de teléfono, y advierte que solo se puede registrar **un webhook por app** de Meta (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.whatsapptrigger).
- El nodo **Facebook Trigger** también puede suscribirse al objeto `whatsapp_business_account`, con eventos: actualización de estado de plantilla, cambio de nombre del número, cambio de calidad del número, revisión de cuenta y actualización de cuenta; requiere permiso `whatsapp_business_management` si se opera como Solution Partner, y que la app propia (no compartida) esté suscrita a la WABA; la propia documentación de n8n recomienda usar el `WhatsApp Trigger` en su lugar porque cubre el doble de eventos (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.facebooktrigger/whatsapp/).

## Lo que NO es posible / limitaciones duras

- **No** se puede seguir usando la On-Premises API: fue descontinuada el 23 de octubre de 2025 (fuente arriba). Cualquier diseño debe asumir Cloud API únicamente.
- **No** hay API para publicar Estados/Stories de WhatsApp.
- **No** existe una "lista de difusión" nativa de la API: todo envío masivo son N llamadas individuales al endpoint de mensajes, sujetas al límite de mensajería vigente y a reglas de plantilla.
- **No** se puede enviar texto libre (no-plantilla) a un contacto que nunca ha escrito, o cuya última interacción fue hace más de 24 horas: se requiere plantilla aprobada.
- La **Groups API**, aunque existe, **no** es utilizable con un número que ya está en la app WhatsApp Business o en coexistencia, y **exige OBA** — no encaja con un MVP de bajo presupuesto ni resuelve "difusión a clientes".
- **No** se puede tener el mismo número simultáneamente en la app y en Cloud API sin pasar por el flujo específico de **Coexistence vía Embedded Signup**; no hay una forma "manual" de lograr esto fuera de ese flujo.
- El límite por-usuario de plantillas de marketing **no es configurable ni consultable como cifra fija** por la empresa; es una caja negra dinámica de Meta.
- El número de prueba de Meta **no sirve para producción**: tope de 5 destinatarios fijos.
- **No** se pueden almacenar ni procesar datos de pago (tarjetas) dentro del flujo de WhatsApp — el carrito/checkout de catálogo depende de integraciones de pago externas o de que el pedido se cierre fuera de banda (fuera del alcance de este documento pero relevante para Fase 10/Meta Ads y comercio).
- **No** hay garantía contractual de "entrega" solo porque la API responda 200 al `POST /messages`: la respuesta inicial únicamente confirma que el mensaje fue aceptado para procesamiento (`accepted`, `held_for_quality_assessment` o `paused`); el estado real de entrega llega después por el webhook `statuses` (https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages). Esto es coherente con la regla del proyecto de "nunca asumir éxito solo por HTTP 200".

## Requisitos previos (cuentas, roles, permisos, verificaciones, modo desarrollo vs producción)

1. Cuenta de **Meta Business Portfolio** (antes Business Manager) que sea dueña del **WABA (WhatsApp Business Account)**.
2. **App de Meta for Developers** con el producto WhatsApp añadido; en modo Development solo puede enviar/recibir con números de prueba y hasta 5 destinatarios allowlisted.
3. Para producción: **App Review** aprobado con Advanced Access sobre `whatsapp_business_messaging` y, si se administran plantillas/configuración de la WABA de terceros, `whatsapp_business_management` (https://developers.facebook.com/documentation/business-messaging/whatsapp/permissions).
4. **Business Verification** del Business Portfolio (documentos legales: licencia de negocio, NIT/registro, dirección/teléfono coincidentes) — necesaria para desbloquear niveles de mensajería más altos y para muchas funciones avanzadas.
5. **System User** con token de larga duración para integraciones server-to-server como n8n, en lugar de tokens de usuario personal que expiran (https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens/).
6. **Embedded Signup** (recomendado) para conectar el número real del dueño, con la opción de **Coexistence** si se quiere conservar la app WhatsApp Business en su celular.
7. **Display name** del número sujeto a revisión de Meta (debe coincidir razonablemente con el nombre del negocio).
8. **Official Business Account (OBA)** — opcional, requiere solicitud aparte y criterios adicionales (p. ej., cobertura de prensa); no es un bloqueante para el MVP.
9. Webhook con **URL pública HTTPS** verificable (necesario incluso en fase local: implica túnel público tipo ngrok/Cloudflare Tunnel mientras el sistema corre en Docker local en Windows, dado que Meta no puede llamar a `localhost`).

## Webhooks (eventos, requisitos de URL, verificación, firma, deduplicación, comportamiento en modo desarrollo)

- **Requisito de URL**: pública, HTTPS, alcanzable por los servidores de Meta; en desarrollo local (Docker en Windows) se necesita un túnel (ngrok, Cloudflare Tunnel, etc.) apuntando al contenedor n8n.
- **Verificación inicial**: handshake `GET` con `hub.mode=subscribe`, `hub.verify_token` (definido por el desarrollador) y `hub.challenge`; el servidor debe responder 200 con el `hub.challenge` crudo si el token coincide.
- **Firma de cada evento**: header `X-Hub-Signature-256: sha256=<hex>` calculado con HMAC-SHA256 sobre el cuerpo crudo usando el App Secret; debe verificarse antes de confiar en el payload.
- **Deduplicación**: Meta reintenta el envío del webhook si no recibe 200 a tiempo, lo que puede generar notificaciones duplicadas; el consumidor (n8n / Error Handler) debe deduplicar por `message.id` en `messages` o por el identificador del `status` en `statuses`, coherente con el requisito de idempotencia del proyecto.
- **Campos principales**: `messages` (mensajes entrantes: texto, imagen, audio, interactive replies, button replies — y estados salientes `sent/delivered/read/failed`, este último con `error.code`), `message_template_status_update` (aprobación/rechazo/pausa de plantillas), y campos de cuenta (`account_update`, `account_review_update`, `account_alerts`), además de eventos de coexistencia como `account_offboarded`/`account_reconnected`.
- **Modo Development**: algunos webhooks no se entregan si la app no ha pasado App Review; solo se reciben eventos relacionados con números/destinatarios de prueba.
- **Suscripción por app**: solo se puede registrar **un webhook por app** de Meta (limitación documentada por n8n); si se necesitan múltiples destinos, se debe redistribuir internamente desde el Orchestrator de n8n.

## Límites, cuotas y costos

- **Niveles de mensajería** (por Business Portfolio, no por número): 250 (default) → 2,000 (tras verificación o volumen con calidad alta) → 10,000 → 100,000 → Ilimitado (escalamiento automático según calidad + uso ≥50% del límite vigente en 7 días).
- **Límite por-usuario de marketing templates**: dinámico, no publicado como número fijo; error 131049 si se excede.
- **Tamaños de media**: imagen 5 MB, audio 16 MB, video 16 MB, documento 100 MB, sticker 100–500 KB.
- **Expiración de media**: URL de descarga 5 minutos; media subido vía API ~30 días; media de webhooks entrantes ~7 días para descarga.
- **Precio**: por mensaje de plantilla entregado (desde el 1 de julio de 2025), diferenciado por categoría (Marketing / Utility / Authentication) y por país del destinatario; mensajes de servicio (no plantilla, dentro de ventana de 24 h) son gratis; Utility/Authentication también son gratis si caen dentro de una ventana de servicio activa.
- **Colombia**: Meta documenta explícitamente un ajuste de tarifas ("higher utility and authentication rates") efectivo el 1 de octubre de 2025; las **cifras exactas en USD/COP no pudieron verificarse en una página pública sin autenticación** (el rate card detallado de Meta requiere login de Business Manager) — **NO VERIFICADO** el monto preciso; fuentes de terceros (agregadores) citan cifras del orden de fracciones de centavo de USD por mensaje de utility/authentication y ~1.4 centavos USD por mensaje de marketing en Colombia, pero como no provienen de developers.facebook.com no se pueden dar como verificadas.
- **Nivel gratuito**: no hay una cuota mensual gratuita fija de mensajes de plantilla; lo gratuito es "servicio dentro de ventana de 24h" y "utility/authentication dentro de ventana de 24h", que en la práctica es donde puede vivir gran parte de la conversación reactiva con clientes (Customer Agent) sin costo, siempre que el cliente haya escrito primero.
- **Costo del "menú matutino proactivo" al dueño**: si el dueño no ha escrito en las últimas 24 h, ese mensaje debe ser una plantilla **Utility** (o Marketing, según cómo se categorice), y por tanto tiene costo por envío; si el dueño responde primero cada mañana (p. ej., "buenos días" a las 7am antes de que el sistema le hable), la interacción cae dentro de ventana de servicio y es gratis. Diseño recomendado: usar Telegram (gratuito, sin restricciones de plantilla) para el control diario, y reservar WhatsApp para lo que realmente debe llegar al dueño por ese canal.

## Implicaciones para el diseño del AI Marketing Agent (concretas, accionables)

1. **Priorizar Telegram para el control diario del dueño** (menú matutino, aprobaciones, comandos), tal como ya define el requerimiento original; usar WhatsApp Cloud API principalmente para **Customer Agent** (atención a clientes) y, opcionalmente, como canal de notificación puntual al dueño cuando ya exista ventana de servicio abierta (evita costos de plantilla).
2. **No diseñar ninguna función sobre "Estados" ni "listas de difusión" de WhatsApp**: el requerimiento debe interpretarse como "publicar en Facebook/Instagram" para contenido y "atender/enviar mensajes 1 a 1" para WhatsApp; cualquier "difusión" a varios clientes se modela como un loop de N envíos individuales de plantilla, con control de límite de nivel de mensajería y de límite por-usuario (manejar el error 131049 con reintento diferido ≥24h, nunca en loop agresivo).
3. **Modelar en PostgreSQL el estado de plantillas** (`waba_templates`: name, category, status, language, components) y **el estado de la ventana de servicio por conversación** (`conversations.last_customer_message_at`) para decidir en runtime si un mensaje saliente puede ser de texto libre (gratis) o debe forzar una plantilla (con costo), evitando llamadas fallidas o cobros innecesarios.
4. **Decisión de número de WhatsApp**: para el MVP, usar el **número de prueba de Meta** (máx. 5 destinatarios) solo en Fase 1-6 de desarrollo; antes de Fase 7 (WhatsApp real) decidir explícitamente si se migra el número personal/comercial del dueño mediante **Coexistence** (conserva la app y el historial reciente, pero con límites de sync de 180 días / 14 días de media y throughput de 20 mps) o si se usa un **número nuevo dedicado** para evitar cualquier riesgo sobre el número personal. Dado que el proyecto es "uso personal y familiar" con volumen bajo inicialmente, un número nuevo dedicado reduce riesgo operativo (menos dependencia de sincronización, menos riesgo de perder funciones de la app) al costo de tener que reconstruir contactos.
5. **Publisher de WhatsApp** (`52_PUBLISH_WhatsApp` en la estructura propuesta) debe:
   - Verificar plantilla `APPROVED` antes de enviar.
   - Registrar `message_id` devuelto por la API y esperar el webhook `statuses` antes de marcar como "entregado" (nunca asumir éxito por HTTP 200, cumpliendo la regla #16 del requerimiento).
   - Implementar deduplicación por `message_id`/`publication_id` en PostgreSQL antes de reintentar (cumpliendo la regla de idempotencia #17).
6. **Error Handler global** debe interpretar específicamente el código **131049** (límite por-usuario de marketing) como "no reintentar antes de 24h" y no como error transitorio de red, para no violar la política de reintentos (regla #18) ni empeorar la reputación del número.
7. **Webhook receptor de WhatsApp** (`02_CHANNEL_WhatsApp`) debe: exponer HTTPS público (túnel en local), verificar `X-Hub-Signature-256` con el App Secret, responder rápido (200) y procesar de forma asíncrona, y deduplicar eventos por `message.id`/timestamp antes de disparar el Customer Agent.
8. **No** planear la función de "grupos de WhatsApp" ni "catálogo/carrito" para el alcance actual: Groups API exige OBA y es incompatible con coexistencia; catálogo/carrito depende de Commerce Manager, mejor evaluarlo junto con Meta Ads en Fase 10.
9. **Presupuestar costo variable real**: cada publicación proactiva por WhatsApp al dueño o cada campaña saliente a clientes debe registrar categoría de plantilla y país destino en `agent_logs`/`marketing_events` para poder estimar costo antes de enviar (coherente con la regla #37 de registrar `estimated_cost`), dado que el pricing es ahora por mensaje entregado y varía por categoría/país/trimestre.
10. **Versión de API**: fijar la integración a una versión reciente y estable de Graph API (p. ej. v24.0 o superior, vigente hasta 2028) y documentar en `.env`/config la variable `META_GRAPH_API_VERSION`, dado que Meta deprecia versiones cada ~2 años y el sistema debe poder actualizarse sin rediseño.

### Implicación para el diseño

1. **Sí es viable presupuestar `estimated_cost` con cifras reales**: al costo actual, Utility/Authentication fuera de ventana de servicio cuestan del orden de **0.0006–0.0008 USD por mensaje** (≈2.2–2.9 COP) y Marketing **0.0125 USD por mensaje** (≈46 COP), independientemente del volumen para Marketing y con descuentos por volumen mensual para Utility/Authentication. Esto es un costo marginal muy bajo por mensaje individual (bajo el volumen esperado de un proyecto "uso personal y familiar" multiempresa pequeño), lo que **reduce el riesgo económico** de usar WhatsApp para el "menú matutino proactivo" al dueño (sería una plantilla Utility, ~2.9 COP/mensaje al nivel base) frente a lo que el informe original dejaba abierto como incógnita.
2. Con esta cifra, **no hay razón económica fuerte para excluir WhatsApp** del "menú matutino proactivo" únicamente por costo — el costo por mensaje es marginal incluso a bajo volumen; la recomendación previa de este documento de usar Telegram para el control diario del dueño sigue siendo válida por otras razones (cero fricción de plantillas aprobadas, sin riesgo de rate-limit ni de rechazo de contenido), pero el argumento de "costo" deja de ser el principal driver de esa decisión.
3. Para reengagement de clientes fuera de la ventana de 24 h (mensajes proactivos de marketing), el costo por mensaje (~46 COP / 0.0125 USD) sigue siendo bajo en términos absolutos, pero como es tarifa plana sin descuento por volumen, una campaña masiva a miles de clientes sí acumula un costo total no trivial (p. ej., 10,000 mensajes de marketing ≈ 460,000 COP); el diseño de `52_PUBLISH_WhatsApp`/`agent_logs` debe multiplicar `tarifa_categoria(country=CO) × destinatarios` antes de disparar una campaña, usando el endpoint público o el CSV oficial (ver Evidencia) como fuente de la tarifa vigente, refrescada trimestralmente (1 ene/abr/jul/oct).
4. Recomendación concreta de implementación: no hard-codear estas cifras de forma permanente en el código; guardarlas en una tabla de configuración (`whatsapp_pricing`: country, category, min_volume, max_volume, rate, currency, effective_date) actualizable manualmente cada trimestre (coincidiendo con los ciclos de actualización de Meta: 1 ene/abr/jul/oct), y usarla para calcular `estimated_cost` en `agent_logs`/`marketing_events`, en lugar de asumir que la tarifa es estática indefinidamente.
5. Dado que el endpoint público de `whatsappbusiness.com` no es una API de datos formalmente documentada/versionada por Meta para consumo de terceros (es el backend interno de un bloque de WordPress), **no se recomienda integrarlo en producción como fuente en vivo** dentro de n8n; se recomienda en su lugar descargar periódicamente (manual o vía tarea programada) el CSV oficial de rate card para COP publicado en `developers.facebook.com/documentation/business-messaging/whatsapp/pricing` y actualizar la tabla de configuración desde ahí, o repetir esta misma consulta de verificación manualmente cada trimestre.

### Puntos no verificados

- **Coincidencia exacta letra-por-letra entre la tarifa vigente hoy (1 jul 2026) y la tarifa que entró en vigor el 1 de octubre de 2025 para Colombia**: se infiere con alta confianza porque el changelog oficial no vuelve a mencionar a Colombia en las actualizaciones de enero, abril o julio de 2026, pero no se encontró una tabla oficial que muestre explícitamente "tarifa Colombia en octubre 2025" congelada en el tiempo (los rate cards descargables solo muestran el estado vigente actual, no el histórico numérico exacto de cada trimestre).
- **Estabilidad/soporte del endpoint `wp-json/wab/v1/pricing`**: es un endpoint funcional de WordPress detrás del bloque "pricing calculator" del sitio `whatsappbusiness.com`, no una API pública documentada con contrato estable ni versión; Meta podría cambiar su ruta, parámetros o formato sin aviso, por lo que no debe tratarse como integración de producción, solo como método de verificación puntual.
- **Redondeo de las cifras USD**: el endpoint devuelve USD con 4 decimales (p. ej. 0.0008); no se pudo confirmar si Meta factura con más decimales de precisión internamente o si 0.0008 USD es ya la cifra final de facturación por mensaje.
- **Si existen tarifas distintas para "Authentication-International"** (categoría mencionada en la configuración de la calculadora vía `authIntlMarkets`, aplicable cuando el remitente de la plantilla de autenticación es de un país distinto al destinatario) para el caso específico de Colombia como mercado destino: no se consultó esa variante en esta sesión: el documento original y esta ampliación asumen Authentication estándar (mismo país emisor/receptor), que es el caso relevante para este proyecto (dueño y clientes en Colombia).
