# Instagram Platform API (publicación, comentarios, mensajes, insights)

Fecha de verificación: 2026-09-21

## Resumen ejecutivo (5-10 viñetas con lo que más impacta el diseño)

- Solo cuentas Instagram **profesionales** (Business o Creator) son soportadas; las cuentas **personales quedan fuera** de toda la Instagram Platform API. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login)
- Existen **dos rutas de acceso** con permisos, hosts y capacidades distintas: "Instagram API with Facebook Login" (`graph.facebook.com`, requiere Página de Facebook vinculada) e "Instagram API with Instagram Login" (`graph.instagram.com`, sin Página). (https://developers.facebook.com/docs/instagram-platform/overview)
- La publicación (`POST /{ig-user-id}/media` + `media_publish`) exige que la imagen/video estén en una **URL pública**; la API descarga el archivo vía cURL. **No admite subida binaria/multipart.** (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- El formato de imagen soportado es **exclusivamente JPEG** (MPO/JPS no soportados). (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- El límite de publicación vía API es de **50 contenedores publicados por cuenta de Instagram en una ventana móvil de 24 horas** (`GET /{ig-user-id}/content_publishing_limit`, campo `config.quota_total`). Fuentes de terceros citan cifras distintas (25 o 100); la cifra verificada en la documentación oficial actual es 50. (https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit/)
- **No existe programación nativa** de publicaciones vía API (no hay parámetro `scheduled_publish_time` documentado en Content Publishing); la app debe implementar su propio scheduler y disparar `media_publish` en el momento deseado.
- **No se puede editar el caption** (ni tags ni media) de una publicación ya publicada vía API; la única vía es hacerlo manualmente desde la app de Instagram. (búsqueda de soporte, ver sección "Puntos NO verificados")
- Los **webhooks solo se entregan si la app está en modo Live**; en modo Development no llegan notificaciones aunque la cuenta tenga un rol en la app. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- La métrica `impressions` está **deprecada**: deja de devolver datos para contenido creado a partir del 2 de julio de 2024 en solicitudes hechas después del 21 de abril de 2025; Meta empuja hacia `views`/`reach`. (https://developers.facebook.com/docs/graph-api/changelog/version22.0/, confirmado también por fuentes secundarias de Meta)
- El Messaging API tiene **ventana de 24 horas** para responder a un usuario que escribió primero; **no se permite mensajería proactiva** a usuarios que nunca contactaron a la cuenta (fuera de tags de mensaje aprobados para casos específicos, no promocionales). (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api)
- Para uso familiar/propio (cuentas que administra el mismo desarrollador o que tienen rol de admin en la app), **Standard Access basta y no requiere App Review ni Business Verification**; Advanced Access (necesaria solo para terceros que gestionan cuentas ajenas) sí exige App Review + Business Verification. (https://developers.facebook.com/documentation/instagram-platform/app-review)

## Hechos verificados (cada viñeta termina con la URL fuente entre paréntesis)

- El "Instagram Platform" agrupa las dos rutas oficiales: Instagram API with Instagram Login (host `graph.instagram.com`, autenticación con credenciales de Instagram, token tipo "Instagram User") e Instagram API with Facebook Login (host `graph.facebook.com`, autenticación con credenciales de Facebook, requiere la cuenta de Instagram vinculada a una Página, token tipo "Facebook User o Page"). (https://developers.facebook.com/docs/instagram-platform/overview)
- Ambas rutas exponen: publicación de contenido (imágenes, videos, reels, carruseles), moderación de comentarios, insights/analítica, detección de menciones y mensajería. La ruta con Facebook Login añade además: búsqueda por hashtag, product tagging y partnership ads; la ruta con Instagram Login no da acceso a "ads o tagging". (https://developers.facebook.com/docs/instagram-platform/overview; https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/)
- "The Instagram API with Facebook Login cannot access Instagram consumer accounts" — solo cuentas profesionales (Business/Creator). (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login)
- Instagram API with Instagram Login: "This API setup does not require a Facebook Page to be linked to the Instagram professional account." (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/)
- Permisos vigentes para Instagram API with Instagram Login: `instagram_business_basic`, `instagram_business_content_publish`, `instagram_business_manage_comments`, `instagram_business_manage_messages`, `instagram_business_manage_insights` (este último requerido específicamente para los endpoints de insights). Los nombres antiguos (`business_basic`, `business_content_publish`, `business_manage_comments`, `business_manage_messages`) quedaron deprecados el 27 de enero de 2025. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/; https://developers.facebook.com/docs/instagram-platform/insights)
- Permisos vigentes para Instagram API with Facebook Login: `instagram_basic`, `instagram_content_publish`, `instagram_manage_comments`, `instagram_manage_insights`, `instagram_manage_messages`, `pages_show_list`, `pages_read_engagement`, y opcionalmente `business_management`/`ads_management`/`ads_read` si el usuario gestiona la Página vía Business Manager. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login; https://developers.facebook.com/docs/instagram-platform/insights)
- Token de acceso de Instagram User (ruta Instagram Login): short-lived inicial, canjeable por long-lived válido **60 días**; se puede refrescar si el token long-lived tiene al menos 24h de antigüedad, no ha expirado, y el usuario mantiene concedido `instagram_business_basic`. Un token sin usar durante 60 días expira y no puede refrescarse. (https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login)
- Ruta Facebook Login: el flujo entrega primero un short-lived User Access Token (expira en segundos, ej. `expires_in`), que se intercambia por un long-lived token; para acciones sobre la Página se usa además un Page Access Token obtenido vía `/me/accounts`. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login)
- `POST /{ig-user-id}/media`: el campo de imagen es `image_url`, debe ser una URL pública (la API hace cURL del archivo); solo se soporta JPEG. (https://developers.facebook.com/docs/instagram-platform/content-publishing/)
- `alt_text` está disponible desde el 24 de marzo de 2025 solo para publicaciones de imagen (no soportado en Reels ni Stories). (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- `POST /{ig-user-id}/media_publish` requiere únicamente el parámetro `creation_id` (el ID del contenedor de media, simple o carrusel). (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- Estado del contenedor vía `GET /{ig-container-id}?fields=status_code`: valores posibles `EXPIRED` (no publicado dentro de 24h), `ERROR` (falló al procesar), `FINISHED` (listo para publicar), `IN_PROGRESS` (procesando), `PUBLISHED` (ya publicado). El contenedor expira a las **24 horas**. (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- Carrusel: `media_type=CAROUSEL`, campo `children` con lista de hasta **10** IDs de contenedores marcados con `is_carousel_item=true`; "Carousel images are all cropped based on the first image in the carousel, with the default being a 1:1 aspect ratio" — es decir, todas las imágenes del carrusel se recortan según la proporción de la primera imagen. (https://developers.facebook.com/docs/instagram-platform/content-publishing/)
- Reels: `media_type=REELS` con `video_url` apuntando a un archivo en servidor público; existe soporte de "trial reels" con `trial_params`/`graduation_strategy` (`MANUAL` o `SS_PERFORMANCE`). (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- Stories: `media_type=STORIES` en el mismo flujo de contenedor de dos pasos (crear contenedor → publicar). (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- Límite de publicación vía API: "Instagram accounts are limited to 100 API-published posts within a 24-hour moving period" aparece como texto general en la guía de Content Publishing, pero el endpoint dedicado `content_publishing_limit` documenta el campo `config.quota_total` con valor **50** y `quota_duration` de 86400 segundos (24h) como la cuota real vigente y consultable en tiempo real. NO VERIFICADO cuál de las dos cifras (50 o 100) es la actualmente aplicada de forma consistente a todas las cuentas; se recomienda no asumir un número fijo y **siempre consultar `content_publishing_limit` en tiempo real** antes de publicar. (https://developers.facebook.com/docs/instagram-platform/content-publishing/; https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit/)
- Comentarios: `GET /{ig-media-id}/comments` (lista comentarios), `GET /{ig-comment-id}/replies` (lista respuestas), `POST /{ig-comment-id}/replies` con parámetro `message` (responder), `POST /{ig-comment-id}` para ocultar/mostrar (hide/unhide), `DELETE /{ig-comment-id}` para borrar, `POST /{ig-media-id}` para activar/desactivar comentarios en un medio. (https://developers.facebook.com/docs/instagram-platform/comment-moderation/)
- Permisos para comentarios: ruta Instagram Login → `instagram_business_basic` + `instagram_business_manage_comments`; ruta Facebook Login → `instagram_basic` + `instagram_manage_comments` + `pages_read_engagement` (y `ads_management`/`ads_read` si aplica gestión vía Business Manager). (https://developers.facebook.com/docs/instagram-platform/comment-moderation/)
- Webhooks disponibles incluyen: `comments`, `live_comments`, `mentions`, `messages`, `message_reactions`, `message_echoes`, `messaging_handover`, `messaging_optins`, `messaging_postbacks`, `messaging_referral`, `messaging_seen`, `response_feedback`, `standby`, `story_insights`. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Requisitos de webhook: endpoint HTTPS con certificado TLS válido (no se soportan certificados autofirmados); Meta envía una solicitud GET de verificación con `hub.verify_token`, y notificaciones POST con payload JSON. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Firma de payload: Meta firma cada notificación con SHA-256 en el header `X-Hub-Signature-256`; el receptor debe recalcular el HMAC SHA-256 con el App Secret y compararlo. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- **La app debe estar en modo Live en el App Dashboard para recibir notificaciones webhook**; en modo Development no se entregan webhooks. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Reintentos de webhook: si la entrega falla, Meta reintenta inmediatamente y luego varias veces más con frecuencia decreciente durante las siguientes 36 horas — esto obliga a implementar deduplicación en el receptor (idealmente por ID de evento/comentario/mensaje). (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Messaging API: requiere `instagram_business_basic` + `instagram_business_manage_messages` (ruta Instagram Login). Ventana estándar de **24 horas** para responder a un mensaje entrante; fuera de ese plazo, un envío normal falla. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api)
- **Human Agent tag**: extiende la ventana de respuesta a **7 días** cuando un humano (no un bot) necesita más tiempo; Meta prohíbe explícitamente su uso para mensajes automatizados y dice detectar el abuso de esta etiqueta. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api; búsqueda oficial complementaria)
- Los mensajes/webhooks entregados vía API **no se marcan como leídos** en el inbox de Instagram hasta que se envía una respuesta. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Insights de cuenta (`GET /{ig-user-id}/insights`) incluyen métricas como `reach`, `views`, `accounts_engaged`, `total_interactions`, `likes`, `comments`, `saves`, `shares`, `reposts`, `replies`, `profile_links_taps`, `follows_and_unfollows`, con parámetros `period` (ej. `day`), `metric_type` (`time_series` o `total_value`), `breakdown` (ej. `contact_button_type`, `follow_type`, `media_product_type`) y `timeframe` (solo para demografía: `last_14_days`, `last_30_days`, `last_90_days`, `this_month`, `this_week`). (https://developers.facebook.com/docs/instagram-platform/api-reference/instagram-user/insights)
- `impressions` a nivel de cuenta y de media queda deprecada para v22.0+; datos de medios creados hasta el 1 de julio de 2024 se siguen sirviendo bajo versiones antiguas de la API, pero solicitudes hechas después del 21 de abril de 2025 sobre contenido creado a partir del 2 de julio de 2024 devuelven error. (https://developers.facebook.com/docs/graph-api/changelog/version22.0/)
- Insights de cuenta con menos de 100 seguidores: métricas limitadas/no disponibles. Datos pueden tener hasta 48 horas de retraso. La métrica `online_followers` solo tiene histórico de 30 días. Los datos demográficos devuelven como máximo el top 45. (https://developers.facebook.com/docs/instagram-platform/api-reference/instagram-user/insights)
- Rate limiting: las llamadas a Instagram Platform (excepto mensajería) se contabilizan por par app-usuario en una ventana móvil de 24 horas con la fórmula `Calls within 24 hours = 4800 * número de impresiones del contenido del usuario en ese periodo`. Esto es un límite de tipo Business Use Case (BUC), reportado en el header `X-Business-Use-Case-Usage`, distinto del `X-App-Usage` (Platform Rate Limit general) y del `X-Ad-Account-Usage` (Marketing API). (https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)
- Rate limiting de mensajería: 2 llamadas/segundo para el endpoint de Conversations, 100 llamadas/segundo para el Send API (texto/enlaces/reacciones), y 10 llamadas/segundo para contenido de audio/video, contabilizadas por cuenta profesional de Instagram. (https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)
- Standard Access basta ("es todo lo que tu app necesita") si la app solo sirve la cuenta profesional propia del desarrollador o una cuenta que administra directamente; Advanced Access es obligatoria si la app sirve cuentas profesionales que el desarrollador no posee ni administra, y esa Advanced Access exige App Review y Business Verification. (https://developers.facebook.com/documentation/instagram-platform/app-review; búsqueda complementaria sobre developers.facebook.com/docs/permissions)
- App Review es necesario solo cuando el desarrollador es un "Tech Provider" cuya app sirve a múltiples negocios (terceros) usando Advanced Access, tanto en la ruta Instagram Login como Facebook Login. Para un solo negocio (o varias empresas propias/familiares administradas por el mismo dueño de la app, todas añadidas como cuentas de prueba/roles en el App Dashboard), Standard Access es suficiente y no requiere App Review. (https://developers.facebook.com/documentation/instagram-platform/app-review)

## Lo que NO es posible / limitaciones duras

- **No se puede publicar en cuentas Instagram personales** (no profesionales): la Instagram Platform API exige cuenta Business o Creator. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login)
- **No se puede publicar sin una URL pública** de la imagen/video: el parámetro es `image_url`/`video_url` y Meta hace cURL contra esa URL; no existe upload binario/multipart en `POST /{ig-user-id}/media`. (https://developers.facebook.com/docs/instagram-platform/content-publishing)
- **No existe programación nativa de publicaciones vía API** (no hay un parámetro documentado tipo `scheduled_publish_time` en Content Publishing); la app orquestadora (n8n) debe guardar el calendario y disparar `media_publish` en el momento correspondiente.
- **No se puede editar el caption** de un post ya publicado vía la Graph/Instagram Platform API una vez `PUBLISHED`; solo es editable manualmente desde la app de Instagram. NO VERIFICADO contra una página oficial explícita (no se encontró una declaración directa "editing is not supported" en developers.facebook.com durante esta investigación), pero es consistente con la ausencia de cualquier endpoint `POST/PUT` de edición de caption en la documentación de Content Publishing revisada. Tratar como limitación de diseño hasta confirmación adicional.
- **Un carrusel no admite proporciones de imagen distintas por ítem**: todas las imágenes se recortan según la proporción de la primera imagen del carrusel (comportamiento documentado como "cropped based on the first image"). Se debe normalizar la relación de aspecto de todas las imágenes del carrusel antes de subirlas. (https://developers.facebook.com/docs/instagram-platform/content-publishing/)
- **No se permite mensajería directa proactiva** a usuarios que nunca escribieron primero a la cuenta: la conversación solo puede iniciarla el usuario final (mensaje directo, mención en story, comentario, etc.); no existe un endpoint para "enviar DM en frío" a una lista de usuarios, y hacerlo se considera spam y viola la política de la plataforma. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api; política de Messenger/IG Messaging)
- **Sin webhooks en modo Development**: la app debe pasar a modo Live para recibir cualquier notificación (comentarios, mensajes, menciones), incluso para las propias cuentas del desarrollador que tienen un rol en la app. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- **La ruta Instagram API with Instagram Login no da acceso a "ads o tagging"** (product tagging, partnership ads, hashtag search) — esas capacidades solo existen en la ruta Facebook Login. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/)
- La métrica `impressions` ya **no está disponible** para contenido reciente (creado desde el 2 de julio de 2024, consultado después del 21 de abril de 2025); usar `views`/`reach`/`total_interactions` en su lugar. (https://developers.facebook.com/docs/graph-api/changelog/version22.0/)

## Requisitos previos (cuentas, roles, permisos, verificaciones, modo desarrollo vs producción)

- Cuenta de Instagram debe ser **profesional**: Business o Creator (ambas soportadas; no hay diferencia documentada de capacidades de publicación entre ellas, salvo Stories — ver nota abajo). (https://developers.facebook.com/docs/instagram-platform/overview)
- Ruta **Facebook Login**: la cuenta de Instagram debe estar **vinculada a una Página de Facebook**; se necesita rol de administrador sobre esa Página (o de la Business Portfolio que la reclamó) para autorizar la app vía OAuth. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login)
- Ruta **Instagram Login**: NO requiere Página de Facebook vinculada; el usuario se autentica directamente con sus credenciales de Instagram. (https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/)
- Para uso familiar con varias cuentas propias (varias empresas administradas por el mismo dueño), **Standard Access** es suficiente en cualquiera de las dos rutas: basta con agregar cada cuenta de Instagram como "test user"/con rol de administrador de la app o de la Business Portfolio en el App Dashboard, sin pasar por App Review. (https://developers.facebook.com/documentation/instagram-platform/app-review)
- **Advanced Access** (permisos ampliados para gestionar cuentas de terceros) exige **App Review** y **Business Verification** completa de la empresa/desarrollador. (https://developers.facebook.com/documentation/instagram-platform/app-review)
- Modo **Development** de la app: sirve solo para probar con cuentas que tienen un rol asignado en la app; en este modo **los webhooks no se entregan** (requiere modo Live). Para publicación/lectura vía llamadas API directas (sin webhooks) con cuentas con rol, es razonable esperar que funcione en Development, pero esto no fue confirmado explícitamente en la documentación revisada — NO VERIFICADO punto por punto para cada endpoint (marcar como riesgo a validar en pruebas reales antes de Fase 6).
- Recomendación para el caso de uso "familiar con varias cuentas": usar **Instagram API with Instagram Login** cuando la cuenta no tenga (o no se quiera depender de) una Página de Facebook administrada por otra persona; usar **Instagram API with Facebook Login** cuando la cuenta ya esté vinculada a una Página administrada por un tercero de la familia, siempre que ese tercero otorgue rol de administrador de Página al usuario dueño de la app (o la app se registre bajo la Business Portfolio que reclamó esa Página). Ver sección de implicaciones de diseño.

## Webhooks (eventos, requisitos de URL, verificación, firma, deduplicación, comportamiento en modo desarrollo)

- Campos/eventos disponibles: `comments`, `live_comments`, `mentions`, `messages`, `message_reactions`, `message_echoes`, `messaging_handover`, `messaging_optins`, `messaging_postbacks`, `messaging_referral`, `messaging_seen`, `response_feedback`, `standby`, `story_insights`. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Requisitos de URL: HTTPS con certificado TLS válido; no se aceptan autofirmados. Meta valida el endpoint con una solicitud GET (`hub.verify_token`) antes de activar el webhook. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Verificación de firma: header `X-Hub-Signature-256` con HMAC SHA-256 calculado sobre el payload usando el App Secret; el receptor debe recalcular y comparar. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Modo de la app: **obligatorio modo Live** para recibir cualquier webhook; en Development no llegan notificaciones (aplica incluso a cuentas con rol propio en la app). (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Deduplicación: Meta reintenta entregas fallidas inmediatamente y luego con frecuencia decreciente hasta 36 horas; el receptor debe deduplicar por ID de evento (ej. `comment_id`, `mid` del mensaje) para evitar procesar dos veces la misma notificación — crítico para cumplir el requisito de idempotencia del proyecto. (https://developers.facebook.com/docs/instagram-platform/webhooks)
- Mensajes entregados vía webhook no se marcan como leídos en el inbox de Instagram hasta que el sistema responde. (https://developers.facebook.com/docs/instagram-platform/webhooks)

## Límites, cuotas y costos

- Publicación: `content_publishing_limit` reporta `config.quota_total` = **50** contenedores publicados por cuenta cada `quota_duration` = 86400 segundos (24h), consultable en tiempo real antes de publicar. Existe además una mención textual de "100 API-published posts within a 24-hour moving period" en la guía general de Content Publishing — **discrepancia no resuelta entre dos textos de la misma documentación oficial**; se marca como NO VERIFICADO cuál prevalece y se recomienda diseñar el sistema para siempre consultar la cuota real vía API antes de publicar, en vez de asumir un número fijo. (https://developers.facebook.com/docs/instagram-platform/content-publishing/; https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit/)
- Rate limit general (no mensajería): fórmula BUC `Calls within 24h = 4800 × número de impresiones del contenido del usuario` en ventana móvil de 24h, por par app-usuario; se reporta en el header `X-Business-Use-Case-Usage`. (https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)
- Rate limit de mensajería: 2 llamadas/seg para Conversations, 100 llamadas/seg para envío de texto/enlaces/reacciones, 10 llamadas/seg para audio/video, por cuenta profesional de Instagram. (https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)
- Headers de uso: `X-App-Usage` (Platform Rate Limit general por app), `X-Business-Use-Case-Usage` (límites BUC de Instagram Platform/Marketing API), `X-Ad-Account-Usage` (Marketing API por cuenta publicitaria). (https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)
- Insights de cuenta: datos pueden tener hasta 48 horas de retraso; `online_followers` solo conserva 30 días de histórico; cuentas con menos de 100 seguidores tienen métricas limitadas; desgloses demográficos limitados al top 45. (https://developers.facebook.com/docs/instagram-platform/api-reference/instagram-user/insights)
- Costos: la Instagram Platform API (Graph API estándar) **no tiene costo monetario por llamada documentado** por Meta; los únicos "costos" son de cuota/rate-limit, no facturación. NO VERIFICADO exhaustivamente para todos los casos (ej. WhatsApp Business Platform sí tiene tarificación por conversación, pero eso es un documento aparte fuera del alcance de Instagram).

## Implicaciones para el diseño del AI Marketing Agent (concretas, accionables)

- **Storage de imágenes debe exponer URLs públicas HTTPS** (ej. bucket con acceso público de lectura o servidor propio expuesto vía Cloudflare Tunnel/dominio) antes de llamar a `POST /{ig-user-id}/media`; el diseño de "Storage" (carpeta `storage/generated`) necesita un componente que sirva esos archivos públicamente y de forma temporal (borrar/expirar después de publicar, dado que el contenedor expira a las 24h de todos modos).
- **Forzar JPEG en el pipeline de generación de imágenes**: el Image Generation Agent debe convertir cualquier salida (PNG, WEBP) a JPEG antes de subir, para evitar rechazos de la API.
- **No implementar programación nativa vía Instagram API**: el `SCHEDULE` del flujo de publicación (paso 38 del requerimiento) debe vivir en n8n/PostgreSQL (tabla `publication_queue` con `scheduled_at`) y un workflow con trigger tipo cron/wait que dispare `media_publish` en el momento planeado; no delegar el scheduling a Meta.
- **Consultar `content_publishing_limit` antes de cada intento de publicación** (no asumir 25/50/100 fijo) y registrar el resultado en `publication_results`; si `quota_usage` está cerca del `quota_total`, encolar para el día siguiente en vez de fallar silenciosamente — esto también sostiene el requisito de idempotencia/no publicar dos veces.
- **Verificación de publicación en dos pasos**: 1) poll de `GET /{ig-container-id}?fields=status_code` hasta `FINISHED` antes de llamar a `media_publish`; 2) tras publicar, `GET /{ig-media-id}?fields=id,permalink,timestamp,media_type,media_product_type` para confirmar y guardar el `external_post_id`/`permalink` real — nunca asumir éxito solo por el HTTP 200 del `media_publish`, tal como exige el requerimiento (sección 16).
- **Diseñar el carrusel exigiendo una sola relación de aspecto** en el Creative Agent/Image Generation antes de armar `children`, ya que Instagram recorta todo según la primera imagen; validar esto en el paso "validar formato" del Publisher.
- **Caption inmutable tras publicar**: el Approval flow (sección 15) debe forzar que el copy quede finalizado y aprobado ANTES de `media_publish`, ya que no hay edición posterior por API; cualquier "Cambia el texto" del usuario debe ocurrir en la fase PENDING_APPROVAL, nunca después de PUBLISHED.
- **App en modo Live obligatoria desde el día 1 de Fase 6** para que el Customer Agent reciba webhooks de comentarios/mensajes/menciones; el modo Development solo sirve para probar llamadas API directas (publicar, leer), no para el flujo de atención al cliente basado en webhooks.
- **Implementar deduplicación por ID de evento** en el Error Handler / Customer Inbox (tabla `conversation_messages` con constraint único sobre el ID externo del mensaje/comentario) para absorber los reintentos de 36 horas que hace Meta.
- **Elegir la ruta de acceso por empresa, no globalmente**: para la empresa cuya Página de Facebook administra un familiar distinto al dueño del sistema, usar Instagram API with Facebook Login solicitando que ese familiar otorgue rol de administrador de Página (o se use Business Portfolio compartida); para cuentas de Instagram sin Página o donde no se quiera depender de terceros, preferir Instagram API with Instagram Login. Guardar en `company_social_accounts` qué ruta/host/permmisos usa cada `company_id`, porque los tokens y refresh son distintos por ruta.
- **Refresh proactivo de tokens**: dado que los long-lived tokens duran 60 días y requieren refresco antes de expirar (y no pueden refrescarse si ya expiraron), el sistema necesita un workflow `91_SYSTEM_Backup`-like o un `10_COMPANY_Management` job programado (ej. cada 45 días) que refresque tokens por `company_id` y alerte por Telegram si un refresh falla, para no perder acceso silenciosamente.
- **No prometer mensajería proactiva en el Customer Agent**: cualquier funcionalidad de "contactar leads por Instagram DM primero" queda descartada; el Lead Agent solo puede responder dentro de la ventana de 24h (o 7 días con Human Agent tag aplicado por un humano real) a quienes ya escribieron. Si se necesita outreach proactivo, la alternativa realista es Telegram/WhatsApp (canales donde el dueño controla el contacto) o anuncios pagados (Meta Ads, Fase 10), nunca DM frío de Instagram.
- **Analytics: usar `views`/`reach`/`total_interactions`, no `impressions`**, y no bloquear el diseño de "horario con mejor rendimiento" en una sola métrica; usar `total_interactions` + `reach` con `breakdown` por franja horaria y validar contra el histórico de 90 días antes de generar recomendaciones (cumpliendo la regla FACT/INFERENCE/RECOMMENDATION del requerimiento).
- **Marcar como riesgo de Fase 6** las dos cifras no reconciliadas del límite de publicación (50 vs 100) y las métricas de insights no confirmadas: agendar una prueba real contra una cuenta de prueba antes de comprometer el diseño final del Analytics Agent.

## Ampliación G6: ¿Cuál es la cuota real y vigente de publicaciones por API de Instagram en una ventana de 2

Fecha de verificación de esta ampliación: 2026-09-21

### Respuesta directa

La cifra vigente y más confiable es **50** contenedores publicados por cuenta de Instagram en una ventana móvil de 24 horas, no 100. Esto se confirma no solo por el endpoint dedicado `content_publishing_limit` (`config.quota_total` = 50, como ya reportaba el informe original), sino también por una **segunda sección dentro de la misma guía de Content Publishing** ("Create a carousel container → Limitations") que declara explícitamente "Accounts are limited to 50 published posts within a 24-hour period" — es decir, 2 de 3 menciones oficiales encontradas coinciden en 50. El texto "100 API-published posts within a 24-hour moving period" solo aparece en la sección general "Rate Limit" de esa misma página y todo indica que es texto desactualizado que Meta no sincronizó con el resto del documento. Esto **corrige/refina** lo dejado como NO VERIFICADO en el informe original: ya no se trata de un empate 50-vs-100 entre dos páginas distintas, sino de 50 respaldado por dos fuentes (la sección de carrusel + el endpoint en tiempo real) contra 100 respaldado por una sola sección de la misma guía. Adicionalmente, ambas secciones que mencionan el límite coinciden en que **un carrusel completo cuenta como una sola publicación** hacia la cuota, sin importar cuántos `children` (imágenes/videos) tenga.

### Evidencia

- Endpoint dedicado (fuente primaria consultable en tiempo real): "The maximum number of IG Containers the app user can publish within the `quota_duration` time period (currently **50**)" y "`quota_duration`... currently 86400 seconds, or 24 hours". (https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit/)
- Guía general de Content Publishing, sección "Rate Limit" (texto que da la cifra distinta): "Instagram accounts are limited to **100** API-published posts within a 24-hour moving period." + "Carousels count as a single post." + "This limit is enforced on the `POST /<IG_ID>/media_publish` endpoint..." (https://developers.facebook.com/docs/instagram-platform/content-publishing/)
- **Hallazgo nuevo de esta ampliación**: la misma guía de Content Publishing, en la sección "Create a carousel container → Limitations", dice: "Accounts are limited to **50** published posts within a 24-hour period." y "Publishing a carousel counts as a single post." (https://developers.facebook.com/docs/instagram-platform/content-publishing/) — es decir, la contradicción no es entre dos páginas (guía general vs. endpoint), sino **dentro de la misma página**, entre su sección general de "Rate Limit" (100) y su sección específica de carruseles (50). Esto no estaba señalado en el informe 03 original, que solo comparó la guía general contra el endpoint.
- No se encontró ninguna nota de changelog, fecha de "última actualización" por sección, ni aviso oficial de Meta que explique o reconcilie explícitamente por qué persisten ambos números en la misma guía.

### Implicación para el diseño

- **Diseñar el guardrail determinístico asumiendo 50 como techo real** (no 100): al calcular cuándo encolar publicaciones para el día siguiente, usar como referencia conservadora `quota_total` leído en tiempo real vía `GET /{ig-user-id}/content_publishing_limit` (tal como ya recomendaba el informe original), pero si por algún motivo el sistema necesita un valor por defecto antes de la primera llamada real (ej. para estimar capacidad en el Content Planner sin haber consultado aún la API), usar 50 y no 100 como supuesto de diseño, para evitar sobreestimar el margen disponible.
- **Los carruseles no penalizan la cuota por cada imagen**: dado que "publishing a carousel counts as a single post" (confirmado en dos secciones de la misma guía), el Content Planner puede planificar carruseles de hasta 10 imágenes sin que esto consuma más de 1 unidad de `quota_usage`; no es necesario multiplicar el conteo de cuota por el número de `children` del carrusel.
- **Mantener la recomendación existente de nunca hardcodear el número** y siempre consultar `content_publishing_limit` en tiempo real antes de publicar y antes de encolar, porque aunque esta ampliación reduce la incertidumbre (50 tiene más respaldo textual que 100), Meta no ha corregido/retirado el texto de 100, por lo que no puede descartarse al 100% que sea aplicable a algún segmento de cuentas no documentado explícitamente.
- Dado que el modo automático del requerimiento limita a 5 publicaciones/día por empresa, **ambas cifras (50 y 100) dejan margen amplio** incluso en modo multiempresa con volúmenes moderados; el riesgo real solo aparece si a futuro una sola cuenta de Instagram sirve a un volumen alto de contenido (ej. > 40-45 publicaciones/día combinando posts y carruseles), momento en el cual sí importa saber que el guardrail debe dispararse cerca de 50, no esperar hasta 100.

### Puntos no verificados

- **NO VERIFICADO**: por qué la misma guía oficial de Content Publishing contiene "100" en su sección general de "Rate Limit" y "50" en su sección de límites de carrusel; no se encontró un errata, nota de changelog o versión de API que explique la discrepancia interna.
- **NO VERIFICADO**: si existen variaciones del límite de publicación por tipo/tier de cuenta (antigüedad, volumen histórico, nivel de confianza/Business Verification) — la documentación revisada no menciona tiers para este límite específico de publicación (a diferencia de otros límites de la plataforma como el de mensajería, que sí tiene tiers documentados en otros productos de Meta).
- **NO VERIFICADO empíricamente**: no se realizó una prueba real contra una cuenta de Instagram de prueba publicando más de 50 veces en 24 horas para confirmar en cuál cifra se corta efectivamente la API; el hallazgo de esta ampliación se basa exclusivamente en el texto coincidente de documentación oficial (2 secciones con 50 vs. 1 sección con 100), no en observación directa del comportamiento de la API.
