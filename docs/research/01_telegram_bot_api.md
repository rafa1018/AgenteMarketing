# Telegram Bot API y su soporte en n8n

Fecha de verificación: 2026-09-21

## Resumen ejecutivo (5-10 viñetas con lo que más impacta el diseño)

- El **Telegram Trigger nativo de n8n funciona únicamente por webhook** (HTTPS público); no hace polling (`getUpdates`) por sí mismo. Para exponer n8n local sin IP pública hay que usar un túnel de terceros (Cloudflare Tunnel, ngrok, localtunnel) (https://community.n8n.io/t/telegram-without-webhook-by-polling/107101, https://core.telegram.org/bots/webhooks).
- **El túnel propio de n8n (`--tunnel` / `WEBHOOK_TUNNEL_URL`) fue descontinuado el 2 de marzo de 2026** por problemas operativos y de seguridad; n8n recomienda oficialmente Cloudflare Tunnel, ngrok o localtunnel en su lugar (https://blog.n8n.io/n8n-tunnel-service-discontinued/). Una página de docs.n8n.io (workflow-development) aún menciona el modo túnel — está desactualizada; **gana el blog oficial más reciente**.
- Telegram exige HTTPS real (TLS 1.2+) para webhooks, solo en los puertos **443, 80, 88 o 8443**, y solo acepta conexiones entrantes desde los rangos IP `149.154.160.0/20` y `91.108.4.0/22` (IPv4 solamente) (https://core.telegram.org/bots/webhooks).
- `secret_token` de `setWebhook` (1-256 caracteres) se valida comparando la cabecera `X-Telegram-Bot-Api-Secret-Token` que Telegram añade a cada POST — es el mecanismo oficial para verificar que la petición viene de Telegram y no de un tercero que adivinó la URL (https://core.telegram.org/bots/api).
- `callback_data` de los botones inline está limitado a **1-64 bytes UTF-8**: no cabe un JSON grande ni un `content_id` largo; en el diseño hay que usar IDs cortos (o un hash) y resolver el resto contra PostgreSQL (https://core.telegram.org/bots/api).
- `getFile` limita la descarga a **20 MB** por archivo en la API pública de Telegram, y el `file_path` devuelto es válido solo un tiempo limitado; para archivos más grandes hace falta un Bot API Server local (self-hosted), que sube el límite a 2000 MB (https://github.com/tdlib/telegram-bot-api, NO VERIFICADO el tiempo exacto de expiración del `file_path` contra el texto oficial completo).
- La operación **"Send and Wait for Response"** del nodo Telegram de n8n cubre bien el caso "aprobar/rechazar" simple, pero también depende de un webhook público accesible (mismo requisito que el Trigger) y su salida no siempre trae el `chat.id`/`message_id` completos para operaciones de seguimiento — para un flujo de aprobación robusto con edición de tarjeta (editMessageReplyMarkup) puede ser preferible manejar `callback_query` manualmente con estado en PostgreSQL (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations, https://community.n8n.io/t/telegram-send-and-wait-behaviour/122366).
- El **modo de privacidad** (`/setprivacy` en BotFather) determina si el bot ve todos los mensajes de un grupo o solo comandos/menciones/respuestas; para que el bot procese todo en un grupo hay que desactivar la privacidad o hacerlo administrador (https://core.telegram.org/bots/faq).
- Límites de envío: ~1 mensaje/seg a un mismo chat privado, ~20 mensajes/minuto en un mismo grupo, y ~30 mensajes/seg en total (bulk) antes de recibir `429 Too Many Requests` con `retry_after` en segundos — hay que implementar cola/backoff respetando ese valor, no un backoff inventado (https://core.telegram.org/bots/faq).
- `sendMessage` soporta hasta 4096 caracteres; captions (`sendPhoto`, `sendDocument`, etc.) hasta 1024 caracteres; `sendMediaGroup` acepta entre 2 y 10 elementos — relevante porque el requerimiento pide "cuatro publicaciones para hoy" con imagen+texto, que puede requerir mensajes separados si el copy es largo.

## Hechos verificados (cada viñeta termina con la URL fuente entre paréntesis)

- `setWebhook` requiere `url` (HTTPS) y admite `certificate`, `ip_address`, `max_connections` (1-100, default 40), `allowed_updates`, `drop_pending_updates` y `secret_token` (1-256 caracteres) (https://core.telegram.org/bots/api).
- La respuesta a cada request de webhook debe incluir la cabecera `X-Telegram-Bot-Api-Secret-Token` con el valor configurado en `secret_token`, para que el receptor valide el origen (https://core.telegram.org/bots/api).
- Los puertos soportados para webhook son exactamente **443, 80, 88, 8443**; cualquier otro puerto no funciona (https://core.telegram.org/bots/webhooks).
- El webhook exige TLS 1.2 o superior; SSLv2/3, TLS 1.0 y TLS 1.1 no son soportados (https://core.telegram.org/bots/webhooks).
- Telegram solo envía las peticiones de webhook desde los rangos `149.154.160.0/20` y `91.108.4.0/22`, y no soporta IPv6 para esto (https://core.telegram.org/bots/webhooks).
- Si el servidor del webhook responde con un código distinto de 2xx, Telegram reintenta la entrega del mismo update y "se rinde después de una cantidad razonable de intentos"; mientras no se confirme con 2xx, Telegram sigue reenviando el mismo update (https://core.telegram.org/bots/webhooks; corroborado por https://telegrambots.github.io/book/3/updates/webhook.html). NO VERIFICADO el número exacto de reintentos ni el backoff exacto entre ellos — la documentación oficial no lo cuantifica.
- `getUpdates` (long polling) usa `offset`, `limit` (1-100, default 100) y `timeout`; los `update_id` son secuenciales y crecientes, y si no hay updates nuevos durante al menos una semana, el siguiente `update_id` se elige aleatoriamente en vez de secuencialmente (https://core.telegram.org/bots/api).
- Cada `Update` contiene como máximo uno de los campos opcionales (message, callback_query, etc.) — de ahí que el consumidor deba enrutar por el campo presente (https://core.telegram.org/bots/api).
- `sendMessage`: texto hasta 4096 caracteres tras el parseo de entidades; supera ese límite y la API rechaza la petición completa ("message is too long") en vez de truncar (corroborado por múltiples SDKs oficiales de terceros y n8n docs; NO se pudo extraer el número textual directo de core.telegram.org/bots/api por truncamiento de la página al fetch, pero es consistente en la documentación de n8n: https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- Captions de medios (`sendPhoto`, `sendVideo`, `sendDocument`, `sendMediaGroup`) limitados a 1024 caracteres (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- `sendMediaGroup` requiere un array de **2 a 10** elementos (photos/videos) — solo el primer elemento del grupo puede llevar caption visible del conjunto en la práctica de la API (https://core.telegram.org/bots/api, texto confirmado vía snippets indexados de la propia página oficial).
- `InlineKeyboardButton.callback_data` es UTF-8 de **1 a 64 bytes** (https://core.telegram.org/bots/api).
- `answerCallbackQuery` permite responder a un botón pulsado; su parámetro `text` (tooltip) admite hasta **200 caracteres**, `show_alert` decide si se muestra como alerta modal o notificación pasajera, y `cache_time` (segundos, default 0) indica cuánto puede cachear el cliente la respuesta (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/callback-operations, que documenta el mismo método oficial `answerCallbackQuery`).
- Existen `editMessageText`, `editMessageReplyMarkup`, `editMessageMedia`, `editMessageCaption` como métodos de la Bot API para actualizar un mensaje ya enviado (por ejemplo, la tarjeta de aprobación) sin reenviar uno nuevo (https://core.telegram.org/bots/api; n8n expone al menos `editMessageText` como operación nombrada: https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- `sendChatAction` permite mostrar "escribiendo…", "subiendo foto…", etc.; la acción se muestra durante un tiempo corto (n8n documenta hasta 5 segundos por llamada, según el comportamiento de la API) (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- `getFile` + descarga vía `https://api.telegram.org/file/bot<token>/<file_path>` está limitada a archivos de hasta **20 MB** en la API pública; el link es válido "al menos 1 hora" según terceros basados en la doc oficial (NO VERIFICADO el texto literal exacto de vigencia del `file_path`, no se pudo extraer completo de core.telegram.org por el tamaño de la página).
- Un **Bot API Server local (self-hosted)**, basado en el código oficial abierto por Telegram (`tdlib/telegram-bot-api`), permite subir archivos hasta 2000 MB, descargar sin el límite de 20 MB, usar rutas locales de archivos, webhooks por HTTP (no solo HTTPS), cualquier IP/puerto para el webhook y `max_connections` hasta 100000; requiere `logOut` del bot en el servidor oficial antes de apuntarlo al servidor local (https://github.com/tdlib/telegram-bot-api).
- `setMyCommands` acepta `commands`, `scope` (BotCommandScope: Default, AllPrivateChats, AllGroupChats, AllChatAdministrators, Chat, ChatAdministrators, ChatMember) y `language_code` (ISO 639-1); cada combinación {scope, language_code} tiene su propio límite de 100 comandos (https://core.telegram.org/bots/api, corroborado por documentación de referencia de terceros basada en la misma spec).
- El **modo de privacidad** de un bot en grupos se controla con `/setprivacy` en BotFather: con privacidad activada (default) el bot solo ve comandos dirigidos a él, mensajes vía el bot, o respuestas a sus propios mensajes; con privacidad desactivada, o siendo administrador del grupo, ve todos los mensajes salvo los de otros bots (https://core.telegram.org/bots/faq).
- Límites de envío documentados en el FAQ oficial: evitar más de 1 mensaje/segundo al mismo chat (con margen para ráfagas cortas); máximo ~20 mensajes/minuto en un mismo grupo; para notificaciones masivas a distintos usuarios, ~30 mensajes/segundo sin contratar "broadcast" pagado; violaciones sostenidas producen error 429 (https://core.telegram.org/bots/faq).
- El error 429 ("Too Many Requests") incluye en el cuerpo JSON `parameters.retry_after` con los segundos que hay que esperar antes de reintentar; la recomendación operativa es respetar ese valor literal y no inventar un backoff propio (patrón documentado y consistente en SDKs y comunidad, ver https://core.telegram.org/bots/api para la estructura de error genérica "ok:false, error_code, description, parameters").
- El **Telegram Trigger de n8n** soporta como "Updates" prácticamente todos los tipos de `Update` de la Bot API: Message, Edited Message, Channel Post, Edited Channel Post, **Callback Query**, Inline Query, Chosen Inline Result, Chat Member, My Chat Member, Chat Join Request, Poll, Poll Answer, Message Reaction, y otros más nuevos (Business Connection/Message, Chat Boost, Pre-Checkout/Shipping Query, Purchased Paid Media); el valor por defecto `*` trae "todos excepto Chat Member, Message Reaction y Message Reaction Count" (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/).
- El Telegram Trigger de n8n permite filtrar por "Restrict to Chat IDs" y "Restrict to User IDs" — mecanismo nativo para una allowlist (útil para restringir el bot al dueño o a chats de empresas conocidas) (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/).
- El **nodo Telegram de n8n** organiza operaciones por recurso: **Chat** (Get, Get Administrators, Get Member, Leave, Set Description, Set Title), **Message** (Send Message, Send Photo, Send Video, Send Animation, Send Audio, Send Document, Send Sticker, Send Media Group, Send Location, Send Chat Action, Edit Message Text, Pin/Unpin Chat Message, Delete Chat Message, y **Send and Wait for Response**), **Callback** (Answer Query = `answerCallbackQuery`, Answer Inline Query = `answerInlineQuery`) y **File** (Get File) (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/).
- `answerInlineQuery` en n8n tiene un límite documentado de **máximo 50 resultados por query** y un `cache_time` por defecto de 300 segundos (frente a 0 en Answer Query) (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/callback-operations).
- La operación **"Send and Wait for Response"**, disponible también en Telegram (y en Slack, Gmail, Outlook, Teams, Discord, WhatsApp, email SMTP y el Chat propio de n8n), ofrece tres modos: **Approval** (uno o dos botones configurables), **Free Text** (un campo de texto libre) y **Custom Form** (varios campos editables: texto, textarea, select, número, pre-rellenados desde `$json`) (https://community.n8n.io/t/human-in-the-loop-send-and-wait-for-response-with-multiple-approval-options/84085, resumen que referencia el comportamiento documentado del nodo).
- Para que el Telegram Trigger (webhook) y "Send and Wait for Response" funcionen, n8n necesita que su `WEBHOOK_URL`/`N8N_HOST`+`N8N_PROTOCOL` resuelvan a una URL pública HTTPS alcanzable por Telegram; detrás de un reverse proxy hay que fijar `WEBHOOK_URL` manualmente porque n8n no puede inferir su propia URL pública (https://docs.n8n.io/hosting/configuration/environment-variables/endpoints/, corroborado por comunidad n8n).
- **El servicio de túnel propio de n8n (`--tunnel`, `WEBHOOK_TUNNEL_URL`) fue descontinuado oficialmente el 2 de marzo de 2026**: n8n indica que ya se había eliminado en n8n v2 por "problemas operativos frecuentes y preocupaciones de seguridad", y que en v1 el flag `--tunnel` ahora falla por timeout; recomienda Cloudflare Tunnel, ngrok o localtunnel como alternativas, con la advertencia de tratar el endpoint local "como un punto de entrada de producción: verificar firmas, usar secretos, minimizar el tiempo de exposición" (https://blog.n8n.io/n8n-tunnel-service-discontinued/).
- Cloudflare ofrece **Quick Tunnels** (`cloudflared tunnel --url <puerto-local>`) que exponen un puerto local en una URL pública `*.trycloudflare.com` sin cuenta ni configuración DNS, pensados para pruebas/demos, no para tráfico de producción sostenido (https://developers.cloudflare.com/pages/how-to/preview-with-cloudflare-tunnel/, https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/local-management/create-local-tunnel/).

## Lo que NO es posible / limitaciones duras

- **No existe una forma soportada de recibir updates de Telegram sin exponer un endpoint accesible desde Internet o hacer polling activo**: el Trigger nativo de n8n es webhook-only; hacer `getUpdates` (long polling) puro requeriría un nodo comunitario no oficial (`n8n-nodes-telegram-polling`) fuera del stack "core" que pide el proyecto, o un microservicio propio — no es una función de la Bot API "prohibida", pero sí una limitación de la integración oficial n8n↔Telegram Trigger (https://community.n8n.io/t/telegram-without-webhook-by-polling/107101, https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/).
- **No se puede registrar más de un webhook por bot**: cada llamada a `setWebhook` sobrescribe la anterior; no hay multiplexado nativo de varias URLs para un mismo bot token (consistente con el modelo de la API: un bot = un webhook activo) (https://core.telegram.org/bots/api).
- **No hay garantía documentada de deduplicación automática por parte de Telegram más allá del reenvío por falta de 2xx**: si el propio proceso del bot recibe el mismo update dos veces (por un reintento de Telegram, o por un reinicio de n8n que reprocesa pendientes), la deduplicación real (por `update_id`) es responsabilidad del sistema receptor, no de Telegram. El diseño debe persistir `update_id` procesados en PostgreSQL antes de actuar (idempotencia), tal como ya exige el requerimiento original.
- **`callback_data` no admite payloads grandes** (máx. 64 bytes): no se puede meter un JSON con todo el contenido de la publicación; solo cabe un identificador corto (content_id/short code) que se resuelve contra la base de datos.
- **La descarga de archivos vía la API pública de Telegram está limitada a 20 MB**; para imágenes/documentos más grandes (por ejemplo insumos de campaña) hay que usar el Bot API Server local, que exige correr un binario adicional y hacer `logOut` del bot del servidor oficial (no es "gratis" en complejidad).
- **El servicio de túnel propio de n8n ya no funciona** (descontinuado 2026-03-02); cualquier plan de "correr n8n local + Telegram" debe apoyarse en una herramienta de terceros (Cloudflare Tunnel, ngrok, localtunnel), lo cual introduce una dependencia externa adicional para el entorno de desarrollo local que el requerimiento pide como Fase 1.
- **No hay confirmación oficial de éxito de entrega "leída" por el usuario**: Telegram no expone recibos de lectura para bots; solo se puede confirmar que la API aceptó el envío (`message_id` devuelto), no que el humano lo vio.

## Requisitos previos (cuentas, roles, permisos, verificaciones, modo desarrollo vs producción)

- Crear el bot con **@BotFather** (`/newbot`) para obtener el `TELEGRAM_BOT_TOKEN`; no hay "modo desarrollo" separado de "producción" a nivel de token — es el mismo bot y el mismo token en ambos casos, la diferencia está en si se usa webhook de prueba (n8n test URL) o webhook de producción (https://core.telegram.org/bots/faq).
- Para grupos: decidir si el bot necesita ver todos los mensajes (desactivar privacidad con `/setprivacy` en BotFather, o hacerlo administrador del grupo) o si basta con comandos/menciones (privacidad activada, default) (https://core.telegram.org/bots/faq).
- Para webhooks: se necesita una URL HTTPS pública válida (certificado confiable o autofirmado subido explícitamente), en uno de los 4 puertos soportados, y accesible desde los rangos IP de Telegram — en un entorno LOCAL sin IP pública esto obliga a un túnel de terceros (Cloudflare Tunnel/ngrok/localtunnel) apuntando al puerto donde escucha n8n (https://core.telegram.org/bots/webhooks).
- n8n necesita `WEBHOOK_URL` (o `N8N_HOST` + `N8N_PROTOCOL` + `N8N_PORT` calculados correctamente) apuntando a la URL pública real del túnel, y si hay reverse proxy, `N8N_PROXY_HOPS=1` (https://docs.n8n.io/hosting/configuration/environment-variables/endpoints/).
- Credencial de Telegram en n8n = solo el `Access Token` del bot (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/, enlaza a la página de credenciales).
- La verificación de la URL de webhook con `getWebhookInfo` (permite ver `last_error_message`, `pending_update_count`, etc.) es la forma oficial de diagnosticar problemas de entrega (referenciado indirectamente por el ecosistema; método documentado en la Bot API).

## Webhooks (eventos, requisitos de URL, verificación, firma, deduplicación, comportamiento en modo desarrollo)

- **Eventos**: cualquier tipo de `Update` puede filtrarse con `allowed_updates` en `setWebhook` (o en el Telegram Trigger de n8n eligiendo qué "Updates" escuchar): message, edited_message, channel_post, edited_channel_post, callback_query, inline_query, chosen_inline_result, chat_member, my_chat_member, chat_join_request, poll, poll_answer, message_reaction, etc. (https://core.telegram.org/bots/api, https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/).
- **Requisitos de URL**: HTTPS obligatorio (TLS ≥1.2), puertos 443/80/88/8443, IP de origen restringida a los rangos de Telegram, certificado confiable o autofirmado subido explícitamente (https://core.telegram.org/bots/webhooks).
- **Verificación/firma**: el mecanismo oficial es el `secret_token` configurado en `setWebhook`, comparado contra la cabecera `X-Telegram-Bot-Api-Secret-Token` en cada request entrante; no hay firma criptográfica HMAC del cuerpo (a diferencia de, por ejemplo, Meta) (https://core.telegram.org/bots/api).
- **Deduplicación**: Telegram no deduplica por el receptor; simplemente reintenta el mismo `update_id` si no recibe 2xx. El sistema receptor debe registrar `update_id` procesados (o `message_id`/`callback_query.id`) en PostgreSQL para descartar reprocesos, cumpliendo el requisito de idempotencia del proyecto (https://core.telegram.org/bots/webhooks; NO VERIFICADO el número exacto de reintentos).
- **Comportamiento en modo desarrollo**: n8n ofrece una "Test webhook URL" que se activa con "Listen for test event" y permanece activa solo ~120 segundos, mostrando el payload en el editor — útil para depurar el mapeo de campos, pero no sustituye el webhook de producción activo permanentemente (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/workflow-development, aplicable también al patrón de Telegram Trigger). Para desarrollo local con Telegram real, hace falta un túnel (Cloudflare/ngrok) apuntando al n8n local, dado que el túnel propio de n8n está descontinuado.

## Límites, cuotas y costos

- `max_connections` de webhook: 1-100, default 40 (https://core.telegram.org/bots/api).
- `getUpdates`: `limit` 1-100 (default 100) (https://core.telegram.org/bots/api).
- Texto de `sendMessage`: 4096 caracteres. Caption de medios: 1024 caracteres.
- `sendMediaGroup`: 2 a 10 elementos.
- `callback_data`: 1-64 bytes UTF-8.
- `getFile` (API pública): 20 MB de descarga. Local Bot API Server: hasta 2000 MB de subida, sin límite documentado de descarga.
- `answerInlineQuery`: máximo 50 resultados; `cache_time` default 300 s.
- Envíos: ~1 msg/seg por chat privado; ~20 msg/min por grupo; ~30 msg/seg en total sin broadcast pagado; sobre 429 usar `retry_after` (https://core.telegram.org/bots/faq).
- Broadcast pagado (vía @BotFather, Telegram Stars): hasta 1000 mensajes/seg, requiere balance ≥100.000 Stars y ≥100.000 usuarios activos mensuales — **no aplica** al alcance de este proyecto (uso interno/familiar, pocos chats) (https://core.telegram.org/bots/faq). NO VERIFICADO contra un anuncio oficial adicional fuera del FAQ.
- `setMyCommands`: 100 comandos por combinación {scope, language_code}.
- Costo de la Bot API en sí: **gratuito**; los costos del proyecto vendrán de IA (OpenAI/Anthropic) e infraestructura (Docker/VPS), no de Telegram.

## Cambios recientes y deprecaciones relevantes (2024-2026)

- **2026-03-02**: n8n discontinúa su servicio de túnel propio (`--tunnel`, `WEBHOOK_TUNNEL_URL`); ya estaba eliminado en n8n v2 y ahora falla también en v1. Alternativas oficiales recomendadas: Cloudflare Tunnel, ngrok, localtunnel (https://blog.n8n.io/n8n-tunnel-service-discontinued/).
- Comunidad reporta bugs activos en 2026 sobre "Send and Wait for Response" de Telegram: salida incompleta (falta `chat.id`/`message_id` completos), casos donde el trigger se dispara varias veces para un mismo `callback_query`, y problemas de `WEBHOOK_URL` mal resuelto tras reverse proxy — a tener en cuenta como riesgos de implementación, no como límites de la API de Telegram en sí (https://github.com/n8n-io/n8n/issues/15483, https://github.com/n8n-io/n8n/issues/23489, https://community.n8n.io/t/telegram-send-and-wait-behaviour/122366).
- La Bot API sigue evolucionando (Business Connection/Message, Chat Boost, Purchased Paid Media, Message Reaction aparecen como tipos de update relativamente recientes soportados por el Telegram Trigger de n8n), lo que indica una API activa y con soporte actualizado en n8n a la fecha de verificación (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.telegramtrigger/).

## Implicaciones para el diseño del AI Marketing Agent (concretas, accionables)

1. **Fase 1 (infraestructura local) debe incluir explícitamente un túnel de terceros** (Cloudflare Tunnel recomendado por ser gratuito y sin cuenta para "quick tunnels") como pieza del stack de desarrollo, ya que el túnel propio de n8n no es una opción viable desde 2026-03-02. Documentarlo en el README y en `.env.example` (por ejemplo `PUBLIC_TUNNEL_URL`), y aclarar que es solo para desarrollo — en VPS (Fase 11) se reemplaza por un dominio/certificado real, sin túnel.
2. **Usar `secret_token` de `setWebhook`** desde el día uno (aunque el flujo pase por n8n) y validar la cabecera `X-Telegram-Bot-Api-Secret-Token` en el primer nodo del workflow `01_CHANNEL_Telegram`, rechazando cualquier request que no la traiga o no coincida — es la única verificación de origen que ofrece Telegram para webhooks.
3. **Idempotencia obligatoria a nivel de aplicación**: registrar `update_id` (y `callback_query.id` para botones) en una tabla (`agent_logs` o una tabla dedicada) antes de ejecutar cualquier efecto, porque Telegram puede reenviar el mismo update si el workflow tarda o falla en responder 2xx a tiempo. Esto encaja directamente con el requisito de idempotencia (`content_id`, `publication_id`) ya definido en el requerimiento.
4. **Diseñar la tarjeta de aprobación con `callback_data` corto** (ej. `apr:<content_id_corto>:<accion>`) en vez de intentar meter todo el contexto en el botón, dado el límite de 64 bytes; el `content_id` completo y el estado real viven en PostgreSQL (`content_items`/`publication_queue`), y el callback solo dispara una consulta/actualización por ID.
5. **Usar `editMessageReplyMarkup`/`editMessageText`/`editMessageCaption`** para actualizar la tarjeta de aprobación tras un click (quitar botones, marcar "✅ Aprobado por Rafael a las 10:32") en vez de enviar un mensaje nuevo cada vez — reduce ruido en el chat y dobla como registro visual del estado.
6. **Evaluar entre "Send and Wait for Response" nativo de n8n y un manejo manual de `callback_query`**: el nativo es más rápido de construir para aprobación simple (✅/❌), pero dados los bugs reportados en 2026 (salida incompleta, triggers duplicados) y la necesidad de UI conversacional rica (✅ Publicar / ✏️ Modificar / 🔄 Regenerar / ❌ Cancelar + texto libre tipo "Cambia el texto"), se recomienda **manejar el `callback_query` manualmente** vía el Telegram Trigger con estado en PostgreSQL (tabla `conversations`/`conversation_messages`) para tener control total del ciclo de vida de la aprobación, y usar "Send and Wait" solo si en el futuro se necesita algo puntual y simple.
7. **Restringir el bot con la allowlist nativa del Telegram Trigger** ("Restrict to Chat IDs"/"Restrict to User IDs") como primera línea de defensa, y reforzarlo con una tabla `company_social_accounts`/`allowed_telegram_chats` en PostgreSQL que mapee `chat.id` → `company_id`, cumpliendo el aislamiento multiempresa exigido.
8. **Mapeo chat→empresa**: usar `chat.id` (negativo para grupos/supergrupos) como llave; si el dueño gestiona varias empresas desde chats privados distintos (un chat por empresa) o desde un solo chat con selección de empresa por comando, definirlo explícitamente — recomendación: un chat/grupo de Telegram por empresa para evitar mezclar company_id en la sesión conversacional, minimizando lógica de "empresa activa" en memoria.
9. **Privacidad del bot en grupos**: si se decide usar un grupo de Telegram por empresa, desactivar `/setprivacy` o hacer administrador al bot para que reciba todos los mensajes; documentar esta configuración como paso manual de onboarding por empresa.
10. **Manejo de imágenes generadas**: dado el límite de caption (1024) y el límite de `sendMediaGroup` (2-10), el Creative Agent debe truncar o resumir el copy que se muestra dentro de Telegram si excede 1024 caracteres, y separar copy largo en un `sendMessage` adicional en vez de forzarlo en la caption.
11. **Recepción de archivos del usuario** (ej. el dueño envía una foto de referencia): usar `getFile`, respetar el límite de 20 MB, y si el proyecto migra a VPS con necesidades de archivos más grandes, evaluar entonces un Bot API Server local (complejidad adicional: correr `logOut` del bot, mantener otro contenedor) — **no** implementarlo en Fase 1/3 salvo necesidad concreta.
12. **Rate limiting saliente**: implementar una cola simple (o al menos un nodo `Wait`/control de frecuencia) antes de los `sendMessage`/`sendPhoto` masivos del modo automático (hasta 5 publicaciones/día por empresa no es un problema de volumen, pero sí conviene centralizar el envío para respetar 1 msg/seg por chat y capturar `retry_after` si llega un 429).
13. **`setMyCommands`** debe usarse para publicar el menú de comandos (`/hoy`, `/leads`, `/resultados`, etc.) alineado con el "Menú diario" del requerimiento, mejorando la UX sin depender de que el usuario recuerde texto exacto.
