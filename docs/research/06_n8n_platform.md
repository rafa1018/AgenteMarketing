# n8n autoalojado: despliegue Docker + PostgreSQL, capacidades de IA, nodos clave, límites de la Community Edition, backups y despliegue en Windows/VPS

Fecha de verificación: 2026-09-21

## Resumen ejecutivo (5-10 viñetas con lo que más impacta el diseño)

- n8n ya publicó la serie **2.x** (release notes 2.x vigentes) y sigue lanzando minors casi cada semana; hay que **fijar una versión exacta de imagen Docker** (no usar `latest`) para no romper el sistema con un upgrade automático (https://docs.n8n.io/changelog/release-notes-2.x, https://docs.n8n.io/changelog/release-notes-1.x).
- **n8n 2.0 activa los Task Runners por defecto** para ejecutar el Code node en un proceso aislado (por seguridad); el modo `internal` está deprecado/inseguro y el recomendado en producción es `N8N_RUNNERS_MODE=external` con el contenedor sidecar `n8nio/runners` (https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners).
- La licencia **Sustainable Use License (SUL)** permite uso propio, personal, familiar e interno-empresarial gratis para siempre; solo prohíbe revender n8n como servicio o hacer white-label de n8n mismo (https://docs.n8n.io/sustainable-use-license/).
- n8n soporta oficialmente **PostgreSQL** (las últimas 2 versiones mayores activas + 1 adicional de compatibilidad; a jul-2026 eso es 16, 17 y 18) y **SQLite** (por defecto, no recomendado para producción real por n8n) (https://docs.n8n.io/deploy/host-n8n/configure-n8n/choose-n8ns-database).
- En Windows con Docker Desktop, la recomendación oficial de Docker es **no** hacer bind-mount de datos de PostgreSQL sobre el filesystem NTFS de Windows: usar **named volumes** o, si se usa WSL2, guardar los archivos dentro del filesystem Linux de la distro, no en `/mnt/c/...` (https://docs.docker.com/desktop/features/wsl/best-practices/).
- La Community Edition **no incluye** SSO, Variables `$vars`/External Secrets, Environments con Git, log streaming avanzado ni RBAC/proyectos avanzados; sí incluye desde hace poco Folders, Data Tables, debug in editor y la API pública REST (https://docs.n8n.io/deploy/host-n8n/community-edition-features).
- **n8n no permite seleccionar dinámicamente por expresión QUÉ credencial usa un nodo** (el selector de credenciales es fijo en diseño); solo se pueden usar expresiones dentro de algunos campos de la credencial. Para multiempresa con tokens distintos por `company_id` hay que usar HTTP Request node con autenticación genérica (headers) construida por expresión, leyendo el token desde PostgreSQL propio (comunidad de n8n, feature request abierto, no resuelto: https://community.n8n.io/t/dynamic-credential-selection-via-expressions-for-multi-tenant-workflows/236158).
- Los nodos "Send and Wait for Response" (Telegram, Slack, Gmail y otros) sí cubren el patrón de aprobación humana con tipos Approval / Free Text / Custom Form, pausando la ejecución (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- No hace falta **queue mode (Redis + workers)** para un uso familiar/pocas empresas: el modo `regular` (proceso único) es el modo por defecto y funciona bien para volumen bajo; queue mode solo aporta valor con alto volumen concurrente o ejecuciones largas (https://docs.n8n.io/hosting/scaling/queue-mode/).
- El nodo **Guardrails** (LangChain) existe desde n8n 1.119.0 e incluye detección de jailbreak/prompt injection basada en LLM, pero tuvo una vulnerabilidad de bypass corregida en 2.10.0 — no debe ser la única capa de defensa (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.guardrails).

## Hechos verificados (cada viñeta termina con la URL fuente entre paréntesis)

- n8n publica "release notes 2.x" activamente en su changelog oficial, confirmando que la línea 2.x ya es la vigente (https://docs.n8n.io/changelog/release-notes-2.x).
- n8n libera una versión minor casi cada semana, lo que exige una estrategia de actualización controlada, no automática (búsqueda agregada de docs.n8n.io, respaldado por el propio changelog: https://docs.n8n.io/changelog).
- El CLI flag `--tunnel` se elimina en v2.0 (https://docs.n8n.io/changelog/release-notes-2.x — referenciado también en discusión de breaking changes de n8n 2.0).
- En n8n 2.0, todas las ejecuciones del Code node corren sobre Task Runners; el `N8N_RUNNERS_ENABLED` de la era 1.x queda deprecado porque ya viene activado por defecto (https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners).
- El modo `internal` de task runners se describe como "inseguro por diseño" y en camino a eliminarse; el modo `external` (contenedor separado) es el recomendado para producción (https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners).
- Bajo Task Runners en modo seguro, `$evaluateExpression()` deja de funcionar dentro del Code node porque el modo seguro deshabilita evaluar strings como código (comunidad n8n citando el comportamiento documentado; confirmar con changelog 2.0 antes de depender de ello — NO VERIFICADO al 100% en una página propia de docs.n8n.io).
- La Sustainable Use License (SUL) es la licencia por defecto del self-hosted; el texto de la licencia permite "usar o modificar el software solo para fines internos de negocio propio o para uso no comercial o personal" (https://docs.n8n.io/sustainable-use-license/).
- n8n soporta oficialmente PostgreSQL: "las dos versiones mayores de PostgreSQL activamente mantenidas más recientes (17 y 18, a julio de 2026), más una versión mayor adicional por compatibilidad (16)" (https://docs.n8n.io/deploy/host-n8n/configure-n8n/choose-n8ns-database).
- SQLite es la base de datos por defecto en instalaciones self-hosted, ubicada en `~/.n8n/database.sqlite` (https://docs.n8n.io/deploy/host-n8n/configure-n8n/choose-n8ns-database).
- `N8N_HOST` (default `localhost`), `N8N_PORT` (default `5678`), `N8N_PROTOCOL` (default `http`), `N8N_EDITOR_BASE_URL` (sin default, URL pública del editor) y `N8N_PROXY_HOPS` (default `0`, número de reverse-proxies delante de n8n) están documentados en la página de variables de despliegue (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/deployment).
- `WEBHOOK_URL` está **deprecado desde n8n 2.35.0** en favor de `N8N_WEBHOOK_URL`; n8n sigue registrando un warning si se usa la variable vieja (agregado de búsqueda sobre docs.n8n.io — recomendable revalidar el número exacto de versión antes de publicarlo como definitivo: NO VERIFICADO el número de versión exacto, sí el hecho de la deprecación).
- `N8N_SECURE_COOKIE` tiene default `true` y fuerza que las cookies solo se envíen sobre HTTPS (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security).
- `N8N_BLOCK_ENV_ACCESS_IN_NODE` bloquea el acceso a variables de entorno desde expresiones y el Code node; la página general de seguridad la documenta con default `false`, pero el changelog de v2.0 indica que **el default cambia a `true` en n8n 2.0** por seguridad (posible desalineación entre la página de referencia genérica y el comportamiento real en 2.x — verificar la versión exacta del despliegue antes de asumir el default) (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security).
- `N8N_RESTRICT_FILE_ACCESS_TO` limita el acceso del nodo de archivos a directorios específicos, en lista separada por `;` (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security).
- `N8N_BLOCK_FILE_ACCESS_TO_N8N_FILES` tiene default `true` y bloquea el acceso a archivos dentro del directorio `.n8n` y a archivos de configuración definidos por el usuario (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security).
- `EXECUTIONS_DATA_SAVE_ON_SUCCESS` y `EXECUTIONS_DATA_SAVE_ON_ERROR` tienen default `all`; `EXECUTIONS_DATA_SAVE_ON_PROGRESS` default `false`; `EXECUTIONS_DATA_SAVE_MANUAL_EXECUTIONS` default `true` (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).
- `EXECUTIONS_DATA_PRUNE` tiene default `true` (borra datos de ejecuciones antiguas en rolling basis) y `EXECUTIONS_DATA_MAX_AGE` tiene default `336` horas (14 días) (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).
- `EXECUTIONS_TIMEOUT` tiene default `-1` (sin límite) y `EXECUTIONS_TIMEOUT_MAX` tiene default `3600` segundos, tope que un usuario puede configurar por workflow (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).
- `NODE_FUNCTION_ALLOW_BUILTIN` y `NODE_FUNCTION_ALLOW_EXTERNAL` permiten levantar restricciones del sandbox del Code node para módulos built-in y externos respectivamente; sin definir la variable, los módulos externos quedan bloqueados por defecto (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/enable-modules-in-code-node).
- El Code node reemplazó a los nodos Function/Function Item desde n8n 0.198.0 (agregado de búsqueda sobre docs.n8n.io/code/code-node/ — confirmar número de versión si se necesita precisión histórica exacta: NO VERIFICADO el número de versión).
- El nodo Edit Image requiere GraphicsMagick; **la imagen Docker oficial de n8n ya lo incluye**, por lo que solo hay que instalarlo manualmente si se corre n8n fuera de Docker (npm o app de escritorio) (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.editimage).
- El nodo Postgres soporta parámetros posicionales (`$1`, `$2`, ...) en Execute Query, y una opción de "Transaction" para ejecutar varias queries dentro de una transacción con rollback automático si falla (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.postgres).
- El nodo Wait expone `$execution.resumeUrl`, la URL de reanudación generada en tiempo de ejecución, útil para enviarla a un servicio externo (ej. Telegram) y reanudar el flujo cuando llega la respuesta; admite un límite de tiempo opcional tras el cual se reanuda automáticamente (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait).
- El Error Trigger recibe, por defecto, toda la información del error excepto `execution.id` (que requiere que la ejecución esté guardada en la base de datos); si el error ocurre en el nodo trigger del workflow principal, la forma de los datos cambia (más información en `trigger{}`, menos en `execution{}`) (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger).
- El "Error Workflow" se configura por workflow en Settings → Error workflow, apuntando a otro workflow que comienza con un nodo Error Trigger (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger).
- Data Tables (beta) es una feature nativa para guardar datos estructurados dentro de n8n y consultarlos desde workflows, con límite de almacenamiter total por defecto de **50 MB por instancia**, configurable vía `N8N_DATA_TABLES_MAX_SIZE_BYTES`; desde la v1.113 se liberó a todos los planes, incluida Community (https://docs.n8n.io/data/data-tables/).
- La Community Edition self-hosted **incluye API pública REST completa** sin necesitar suscripción Cloud; se activa creando una API key en Settings → n8n API y enviándola en el header `X-N8N-API-KEY` (https://docs.n8n.io/api/authentication/).
- La Community Edition NO incluye SSO, Environments con Git ni External Secrets (Vault/AWS Secrets Manager); esas quedan reservadas a planes de pago (búsqueda agregada sobre docs.n8n.io/deploy/host-n8n/community-edition-features — recomendable revisar la página oficial vigente antes de publicar la lista exacta, dado que n8n mueve features a Community con cada release: parcialmente NO VERIFICADO en el detalle exacto).
- El nodo AI Agent de n8n construye agentes conectando un Chat Model, herramientas (Tools) y memoria; desde n8n 1.82.0 el "agent type" quedó deprecado y todos los AI Agent funcionan como "Tools Agent" (https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent).
- El nodo MCP Server Trigger expone un workflow de n8n como servidor MCP para que clientes MCP externos llamen sus tools; el nodo MCP Client Tool permite que un agente de n8n use herramientas de un servidor MCP externo (SSE endpoint + autenticación Bearer/Header/OAuth2) (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger, https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolmcp).
- El nodo Guardrails (LangChain) existe desde n8n 1.119.0, actúa como capa de validación de entrada/salida de IA, e incluye un guardrail de "jailbreak" (detección de prompt injection) evaluado por un LLM con umbral de confianza por defecto de 0.7 (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.guardrails).
- El "Send and Wait for Response" del nodo Telegram ofrece tres tipos de respuesta: Approval, Free Text y Custom Form (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram/message-operations).
- El "Send and Wait for Response" del nodo Slack permite capturar quién respondió y usa botones interactivos de Slack cuando el Response Type es Approval (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.slack/approvals).
- El CLI de n8n soporta `export:workflow`, `export:credentials --all --decrypted` (exporta credenciales en texto plano para migrar a una instancia con otra encryption key), `import:workflow` e `import:credentials`; los IDs exportados sobrescriben registros existentes con el mismo ID si se re-importan sin cambiarlos (https://docs.n8n.io/hosting/cli-commands/).
- El Facebook Trigger node soporta objetos `page`, `instagram` y `whatsapp_business_account`; sin embargo, la documentación oficial de n8n **recomienda usar el nodo WhatsApp Trigger dedicado en lugar del objeto whatsapp_business_account del Facebook Trigger**, porque el trigger dedicado cubre el doble de eventos; además la app de Meta debe pertenecer al negocio (una app solo "compartida" con el negocio no puede recibir webhooks) (https://docs.n8n.io/integrations/builtin/trigger-nodes/n8n-nodes-base.facebooktrigger/whatsapp/).
- El nodo Facebook Graph API permite hacer llamadas GET/POST/DELETE genéricas contra la Graph API de Meta usando las credenciales `facebookgraph` (https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.facebookgraphapi, https://docs.n8n.io/integrations/builtin/credentials/facebookgraph).
- Cloudflare Tunnel (`cloudflared`) crea un túnel saliente (outbound-only) que no requiere IP pública ni abrir puertos en el router; soporta "Named Tunnels" (persistentes, con dominio propio, requieren cuenta y zona en Cloudflare) y "Quick Tunnels" (efímeros, URL aleatoria, sin necesidad de dominio propio) (https://developers.cloudflare.com/tunnel/, https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/).
- El plan gratuito de ngrok (2026) incluye 3 endpoints online, 1 GB de ancho de banda/mes, 20K requests HTTP/S por mes, 1 "dev domain" y sesiones limitadas a un máximo de 2 horas, con página de advertencia intersticial para visitantes; no es apto para producción continua (https://ngrok.com/docs/pricing-limits/free-plan-limits).
- Docker recomienda, para Windows con WSL2, almacenar el código/datos que se bind-montan en contenedores Linux **dentro del filesystem de la distro Linux (WSL2)**, no en el filesystem de Windows (`/mnt/c/...`), porque el rendimiento de I/O y los eventos `inotify` son mucho peores cruzando la frontera Windows↔Linux (https://docs.docker.com/desktop/features/wsl/best-practices/).
- La imagen `pgvector/pgvector` en Docker Hub publica tags por versión de PostgreSQL, incluyendo `pg17`, `pg18` (y `pg13`–`pg16`), en variantes `bookworm`/`trixie`, siendo un reemplazo directo de la imagen oficial `postgres` con la extensión pgvector precompilada (https://hub.docker.com/r/pgvector/pgvector/tags).
- n8n corre en modo "regular" (proceso único) por defecto, apto para volumen bajo; el modo "queue" (Redis + workers) separa la ejecución del proceso principal para escalar horizontalmente, mediante instancias worker que consumen una cola en Redis (https://docs.n8n.io/hosting/scaling/queue-mode/).

## Lo que NO es posible / limitaciones duras

- **No se puede seleccionar dinámicamente, por expresión, QUÉ credencial usa un nodo** dentro del selector nativo de credenciales de n8n. Es un feature request abierto y no resuelto en la comunidad oficial (https://community.n8n.io/t/dynamic-credential-selection-via-expressions-for-multi-tenant-workflows/236158). Consecuencia directa para el diseño multiempresa: **no se puede tener "una credencial de Facebook" por empresa y elegirla dinámicamente en el mismo nodo Facebook Graph API**; hay que usar HTTP Request node con autenticación por header/query construida con expresiones que lean el token desde PostgreSQL (tabla `company_social_accounts`), o crear un subworkflow por empresa (menos mantenible), o usar una credencial de "Header Auth"/genérica cuyo valor de token se resuelva por expresión en runtime (esto último sí es soportado: expresiones **dentro** de un campo de la credencial, no en la selección de qué credencial usar).
- El AI Agent node **no expone `tokenUsage` en su propia salida**, ni siquiera con "Return Intermediate Steps" activado; el uso de tokens solo aparece en la salida del sub-nodo Model (Chat Model) conectado, no en el nodo Agent contenedor (fuente: comunidad oficial n8n, no una página de referencia dedicada — parcialmente NO VERIFICADO en documentación formal, pero corroborado por múltiples hilos oficiales de soporte: https://community.n8n.io/t/how-to-access-tokenusage-from-a-sub-node-model-within-an-ai-agent/294577).
- El `--tunnel` de n8n **se elimina en v2.0**; no se debe planear su uso para desarrollo a mediano plazo aunque siga apareciendo en tutoriales antiguos.
- El modo `internal` de Task Runners está marcado como inseguro por diseño y en ruta de eliminación; no se recomienda para nada que toque credenciales reales.
- Data Tables tiene un límite total de 50 MB por instancia por defecto (ampliable con `N8N_DATA_TABLES_MAX_SIZE_BYTES`, pero sigue siendo una feature "beta", no un motor de base de datos completo); no reemplaza a PostgreSQL para el Company Brain o el historial de contenido.
- Community Edition **no tiene** SSO ni RBAC/proyectos avanzados ni External Secrets nativos (Vault/AWS Secrets Manager); todo secreto que no sea una "credential" de n8n debe vivir en `.env` + PostgreSQL propio, gestionado por lógica del propio sistema, no por n8n.
- La imagen Docker de PostgreSQL sobre Windows con bind-mount NTFS **no está soportada de forma fiable** para el directorio de datos (`PGDATA`) por incompatibilidades de fsync/POSIX; Docker documenta named volumes o filesystem Linux (WSL2) como única vía recomendada.

## Requisitos previos (cuentas, roles, permisos, verificaciones, modo desarrollo vs producción)

- Cuenta Docker Hub no es obligatoria para descargar `n8nio/n8n` (imagen pública), pero sí es recomendable para evitar rate limits anónimos de Docker Hub en pulls repetidos (NO VERIFICADO el límite exacto vigente en 2026; verificar en https://docs.docker.com/docker-hub/usage/ antes de depender de un número).
- Para exponer webhooks de forma estable (no túneles efímeros) se necesita un dominio propio (para Cloudflare Named Tunnel) o un VPS con IP pública (para reverse proxy con Caddy/Traefik/nginx + TLS).
- Para usar el modo `external` de Task Runners en producción se necesita orquestar un contenedor sidecar adicional (`n8nio/runners`), lo que agrega complejidad de despliegue respecto al modo "todo en un contenedor" (documentado como recomendación oficial, ver sección de Task Runners arriba).
- Para migrar credenciales entre instancias (local → VPS) se necesita la **misma `N8N_ENCRYPTION_KEY`** en ambos entornos, o exportar credenciales con `--decrypted` y volver a cifrarlas con la nueva key al importar.
- No hay "modo desarrollo vs producción" formal como flag único en n8n; la diferencia práctica es: SQLite + `--tunnel` (ya deprecado) = uso exploratorio; PostgreSQL + Task Runners externos + reverse proxy con TLS + queue mode opcional = producción.

## Webhooks (eventos, requisitos de URL, verificación, firma, deduplicación, comportamiento en modo desarrollo)

- n8n construye la URL de webhook combinando `N8N_PROTOCOL` + `N8N_HOST` + `N8N_PORT`, salvo que se fije explícitamente `N8N_WEBHOOK_URL` (antes `WEBHOOK_URL`, deprecado); detrás de un reverse proxy **siempre** hay que fijar esta variable manualmente para que la UI y el registro de webhooks externos (Meta, Telegram) usen la URL pública correcta, no la interna del contenedor (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/deployment y agregados de búsqueda citados arriba).
- Detrás de un reverse proxy también se recomienda `N8N_PROXY_HOPS=1` (o el número de proxies intermedios) para que n8n confíe correctamente en las cabeceras `X-Forwarded-*` (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/deployment).
- n8n distingue entre webhook de **test** (`/webhook-test/...`, solo activo mientras el editor "escucha") y webhook de **producción** (`/webhook/...`, activo solo si el workflow está activado) — comportamiento estándar de n8n, ampliamente documentado en la guía de construcción de workflows; no depende de una única página citable con URL específica, así que se marca **NO VERIFICADO el detalle fino de expiración del modo test** en esta pasada.
- Firma/verificación de webhooks entrantes (p.ej. de Meta con `X-Hub-Signature-256`) **no la hace n8n automáticamente**; hay que verificarla manualmente con el nodo Crypto (HMAC) sobre el raw body del Webhook node. Esto es responsabilidad explícita del diseño del workflow, no una feature nativa de "verificación de firma" en el nodo Webhook.
- Deduplicación de webhooks duplicados (reintentos de Meta/Telegram, o reintentos por timeout) tampoco es automática: se resuelve con el nodo Remove Duplicates (con memoria entre ejecuciones) o, mejor, con una tabla propia en PostgreSQL que registre `external_event_id`/`content_id` ya procesados, según exige el requerimiento de idempotencia del proyecto.

## Límites, cuotas y costos

- Data Tables: 50 MB de almacenamiento total por instancia por defecto, ajustable con `N8N_DATA_TABLES_MAX_SIZE_BYTES`; al superar el límite se bloquean inserciones/actualizaciones manuales y fallan las ejecuciones de workflow que intenten escribir (https://docs.n8n.io/data/data-tables/).
- `EXECUTIONS_TIMEOUT_MAX` limita a 3600 segundos (1 hora) el tiempo máximo configurable por workflow por defecto; `EXECUTIONS_TIMEOUT` global por defecto es `-1` (sin límite) salvo que se fije explícitamente (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).
- `EXECUTIONS_DATA_MAX_AGE` por defecto poda datos de ejecución después de 336 horas (14 días) si `EXECUTIONS_DATA_PRUNE=true` (default) (https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).
- ngrok gratuito (2026): 1 GB/mes de ancho de banda, 20K requests HTTP/S por mes, sesiones de máximo 2 horas — insuficiente para un canal de producción 24/7 (https://ngrok.com/docs/pricing-limits/free-plan-limits).
- Cloudflare Tunnel gratuito: no se documentan límites duros de ancho de banda/solicitudes en la página general para uso normal de un túnel con dominio propio (Named Tunnel), a diferencia de ngrok; requiere tener un dominio administrado en Cloudflare (NO VERIFICADO el límite exacto de requests/ancho de banda del plan gratuito de Cloudflare Tunnel — no se encontró una cifra oficial explícita equivalente a la de ngrok; revisar `developers.cloudflare.com/cloudflare-one/policies/` si se requiere una cifra exacta antes de comprometerse a esta opción para producción).
- Costo de n8n self-hosted: la licencia es gratuita (SUL); el costo real es infraestructura (VPS, dominio, y las APIs de IA/imagen consumidas), no n8n en sí (https://docs.n8n.io/sustainable-use-license/).

## Cambios recientes y deprecaciones relevantes (2024-2026)

- n8n 2.0: Task Runners obligatorios/por defecto para Code node; eliminación del flag `--tunnel`; eliminación de `QUEUE_WORKER_MAX_STALLED_COUNT` y del mecanismo de reintento de "stalled jobs" de Bull (fuente agregada sobre changelog oficial de n8n; recomendable revisar la página `v2.0 Breaking changes` directamente al momento de planear el upgrade, ya que esta pasada tuvo problemas intermitentes de acceso a esa página específica — marcar como **parcialmente NO VERIFICADO** el listado completo de breaking changes de 2.0 y revalidar antes de fijar versión de despliegue).
- `WEBHOOK_URL` deprecado en favor de `N8N_WEBHOOK_URL` (n8n sigue mostrando warning si se usa el nombre antiguo) — **NO VERIFICADO el número de versión exacto** en el que ocurrió (fuentes secundarias mencionan 2.35.0, no confirmado en una página oficial de docs.n8n.io durante esta investigación).
- Guardrails node (LangChain) añadido en 1.119.0, con un fix de seguridad relevante en 2.10.0 por un bypass de jailbreak detection (https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.guardrails).

- Data Tables pasó de beta limitado a disponible en todos los planes (incluida Community) desde la v1.113 (https://docs.n8n.io/data/data-tables/).

## Implicaciones para el diseño del AI Marketing Agent (concretas, accionables)

- **Fijar versión exacta de imagen**: usar `n8nio/n8n:<version>` (nunca `latest`) en `docker-compose.yml`, y decidir explícitamente si se entra en la línea 2.x (con Task Runners obligatorios) o se permanece en una 1.x LTS-like más simple para la Fase 1; dado que el proyecto es nuevo, **entrar directo en 2.x** es razonable, pero exige desde el día uno planear el sidecar `n8nio/runners` en modo `external` si se va a manejar código sensible en el Code node.
- **PostgreSQL**: usar la imagen oficial `postgres:17` (o `pgvector/pgvector:pg17-...` si se decide dejar preparado pgvector desde ya, sin activarlo, para no introducir RAG por moda pero sí dejar la puerta abierta) como pide el requerimiento original. Persistir sus datos con un **named volume**, no con bind-mount a una carpeta de Windows; si el desarrollo ocurre en Windows con Docker Desktop, mover el proyecto (o al menos el volumen) al filesystem de la distro WSL2 en vez de una unidad `E:\` montada vía `/mnt/e`.
- **Encryption key**: generar `N8N_ENCRYPTION_KEY` una sola vez con `openssl rand -hex 32`, guardarla en `.env` (nunca en Git) y **copiarla tal cual al VPS** en la migración; sin ella, las credenciales cifradas en el backup de PostgreSQL son irrecuperables.
- **Webhooks locales**: para Fase 1-3 en local (Telegram primero, sin necesitar webhook público inmediato porque Telegram admite polling), no es urgente resolver exposición pública. Para Fase 6-7 (Facebook/Instagram/WhatsApp, que si requieren webhook HTTPS público), usar **Cloudflare Tunnel con dominio propio (Named Tunnel)** en vez de ngrok, porque ngrok gratuito no aguanta uso continuo (sesiones de 2h, 20K requests/mes) y `--tunnel` de n8n está deprecado.
- **Multiempresa y credenciales**: como n8n no permite elegir credencial por expresión, diseñar los Publishers (Facebook/Instagram/WhatsApp) sobre **HTTP Request node** con autenticación por header construida en runtime desde una tabla propia `company_social_accounts` (tokens cifrados a nivel de aplicación o al menos protegidos por políticas de acceso a PostgreSQL), en vez de depender de "una credencial de n8n por empresa" seleccionable dinámicamente. Esto también evita crear N credenciales de n8n por cada empresa nueva, lo cual sí escala mal.
- **Aprobación humana**: el patrón "Send and Wait for Response" de Telegram (Approval / Free Text / Custom Form) cubre exactamente el flujo GENERATE → SHOW USER → APPROVE del requerimiento; usarlo como primera opción antes de construir una máquina de estados propia en Postgres para esto. Reservar la máquina de estados propia para el estado de negocio (`content_items.status`), no para el mecanismo de espera de respuesta en sí.
- **Idempotencia y webhooks duplicados**: como n8n no deduplica ni verifica firmas por sí solo, implementar explícitamente: (a) verificación HMAC con nodo Crypto para webhooks de Meta, y (b) una tabla `publication_results`/`processed_events` con restricción única sobre `external_post_id`/`event_id` antes de publicar o procesar, tal como exige el requerimiento de idempotencia.
- **Costos de IA**: dado que el AI Agent node no expone `tokenUsage` de forma nativa en su salida, el registro de `model, input_tokens, output_tokens, estimated_cost` (pedido en el requerimiento) debe implementarse leyendo el sub-nodo Model (Chat Model) directamente cuando se use Basic LLM Chain, o vía la API pública de ejecuciones + parseo de metadata cuando se use AI Agent; no asumir que "viene gratis" del nodo Agent.
- **Guardrails**: usar el nodo Guardrails de LangChain como una capa adicional de defensa contra prompt injection en Customer Agent, pero no como única defensa (tuvo un bypass documentado); combinarlo con las reglas de negocio explícitas del Company Brain (nunca revelar system prompt, nunca inventar precios) y con validación determinística (Switch/IF) antes de ejecutar acciones sensibles.
- **Backups**: automatizar `pg_dump` de PostgreSQL + `n8n export:workflow --all` + `n8n export:credentials --all --decrypted` (guardado cifrado aparte, nunca en Git) + copia de `storage/` como rutina periódica (`91_SYSTEM_Backup` del requerimiento), y versionar en Git únicamente los JSON de workflows exportados (sin credenciales, cuyos IDs quedan referenciados mas no expuestos en texto plano).
- **Queue mode**: no implementarlo en Fase 1-9 (uso familiar, pocas empresas); dejarlo como opción documentada para cuando el volumen de ejecuciones concurrentes o la duración de tareas (p.ej. generación de imágenes) empiece a bloquear el proceso único, alineado con el principio de "NO sobrearquitectura" del requerimiento.

**Respuesta directa:** Un Cloudflare Quick Tunnel es técnicamente utilizable durante toda la Fase 1 (sin webhooks de Meta) porque **Telegram sí se puede re-registrar por script** cada vez que cambia la URL (`setWebhook` es una simple llamada HTTP, sin límite de frecuencia documentado). Pero **no es viable como único mecanismo para las Fases 6-7** (Facebook/Instagram/WhatsApp), porque Cloudflare marca los Quick Tunnels explícitamente como "solo para pruebas y desarrollo, sin SLA ni garantía de uptime" y con un tope duro de 200 requests concurrentes, y porque Meta **no expone una API para reconfigurar la URL de callback de webhooks**: el cambio se hace a mano en el App Dashboard (Producto Webhooks → Edit Subscription), repitiendo la verificación `hub.challenge` manualmente cada vez que la URL rota. Esto **confirma y precisa** (no contradice) lo que el informe original ya recomendaba en la sección de Webhooks locales: Quick Tunnel es aceptable para Fase 1-3 con Telegram, pero comprar un dominio y montar un Named Tunnel debe ocurrir **antes de empezar las pruebas repetidas de Meta en Fase 6-7**, no diferirse hasta el VPS de Fase 11.

**Evidencia:**
- Quick Tunnels ("TryCloudflare") generan un subdominio aleatorio en `trycloudflare.com` sin necesitar cuenta de Cloudflare; la documentación oficial afirma explícitamente: "Quick Tunnels are intended for testing and development only. For production use, [create a remotely-managed tunnel]..." y que Cloudflare "don't guarantee any SLA or uptime" para estos túneles, además de un tope de **200 requests concurrentes** (HTTP 429 si se excede) y sin soporte de Server-Sent Events (https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/).
- La documentación no menciona en ninguna página si la URL de un Quick Tunnel persiste entre reinicios del proceso `cloudflared`; por diseño (subdominio generado al vuelo en cada arranque, sin registro DNS persistente) se debe asumir que **cambia en cada reinicio**, a diferencia de un Named Tunnel que sí tiene un hostname fijo vía registro DNS (CNAME al UUID del túnel) (https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/, https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).
- Crear un Named Tunnel con hostname público **sí requiere tener un dominio agregado como zona en Cloudflare** ("Before you publish an application through your tunnel, you must add a website to Cloudflare"); la documentación oficial no ofrece ninguna alternativa gratuita para obtener un hostname público estable sin poseer un dominio (https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/).
- El método `setWebhook` de la Bot API de Telegram no documenta ningún límite de frecuencia de llamadas; solo exige URL HTTPS (puertos soportados: 443, 80, 88, 8443) y, opcionalmente, un certificado propio si es autofirmado — es decir, re-apuntar el webhook de Telegram a una nueva URL de Quick Tunnel es una operación scripteable y repetible sin fricción manual (https://core.telegram.org/bots/api#setwebhook).
- La documentación oficial de Meta (Graph API Webhooks) especifica que la verificación `hub.verify_token`/`hub.challenge` ocurre al configurar el webhook, pero **la configuración/edición de la URL de callback se hace agregando y editando el producto "Webhooks" en el App Dashboard**, no vía un endpoint de la Graph API dedicado a esto; no se encontró documentación de un endpoint tipo "setWebhook" programático equivalente al de Telegram para reconfigurar la URL de callback de una app de Meta (https://developers.facebook.com/docs/graph-api/webhooks/getting-started, https://developers.facebook.com/docs/graph-api/webhooks).
- La documentación de Meta tampoco especifica límites de frecuencia para re-verificar/cambiar la URL de callback, pero al ser un flujo de UI (App Dashboard) y no de API, el costo operativo de repetirlo en cada reinicio de `cloudflared` es manual, no automatizable con un script simple (https://developers.facebook.com/docs/graph-api/webhooks/getting-started).

**Implicación para el diseño:** No es necesario comprar un dominio ni montar un Named Tunnel desde el primer día de la Fase 1. Mientras el desarrollo se limite a Telegram (que además admite polling sin webhook en absoluto, como ya señala este informe), un Quick Tunnel gratuito basta y se puede automatizar con un script que, en cada arranque de `cloudflared tunnel --url http://localhost:5678`, parsee la nueva URL de los logs y llame `setWebhook` automáticamente. Pero **antes de iniciar las pruebas de integración con Facebook/Instagram/WhatsApp (Fase 6-7)**, el proyecto debe presupuestar la compra de un dominio (costo bajo, tipo `.com`/`.dev`, ~10-15 USD/año, no verificado el precio exacto vigente) y configurar un Named Tunnel con cuenta Cloudflare, precisamente porque cada rotación de URL de un Quick Tunnel obligaría a repetir manualmente, por cada app de Meta (Facebook, Instagram, WhatsApp Business), el flujo de edición del App Dashboard y la verificación `hub.challenge` — algo inviable para el ciclo de pruebas iterativo de esas fases. Recomendación concreta: tratar la compra del dominio y el Named Tunnel como un requisito de infraestructura que debe estar listo **al inicio de la Fase 6**, no como algo diferible hasta la migración a VPS de la Fase 11; Telegram puede seguir sobre Quick Tunnel (o incluso polling) durante más tiempo si se prefiere no adelantar el gasto.

**Puntos no verificados:**
- No se encontró una página oficial de Cloudflare que declare explícitamente si la URL de un Quick Tunnel cambia en el 100% de los reinicios o si en algún caso se reutiliza; se infiere el cambio por el diseño del mecanismo (no hay registro DNS ni identidad persistente asociada), pero no hay una frase oficial tipo "the URL changes every time you restart cloudflared" confirmada textualmente en esta pasada. **NO VERIFICADO** literalmente, aunque es la interpretación estándar y ampliamente documentada por terceros del comportamiento de TryCloudflare.
- No se confirmó de forma exhaustiva la inexistencia total de cualquier API de Meta para actualizar la URL de callback de webhooks (por ejemplo, alguna operación vía Graph API sobre el objeto de la app misma); solo se verificó que las páginas oficiales de "getting started" y la página general de Webhooks describen el flujo como configuración en el App Dashboard, sin mencionar un endpoint alternativo. **Parcialmente NO VERIFICADO** — revisar `developers.facebook.com/docs/graph-api/webhooks/subscriptions` (la URL específica devolvió 404 en esta pasada, posible cambio de ruta) antes de descartar por completo una vía programática.
- Precio de referencia de un dominio (~10-15 USD/año) es una estimación general de mercado, **no verificada contra un registrador u oficial de Cloudflare Registrar en esta pasada**; Cloudflare Registrar solo revende dominios a precio de costo sin margen, pero no se confirmó una tabla de precios oficial vigente a 2026-09-21 en esta investigación.
- No se verificó si el tope de 200 requests concurrentes de Quick Tunnels sería relevante en la práctica para el volumen de pruebas de un proyecto familiar/pocas empresas (probablemente no, dado el bajo volumen esperado en Fase 1-7), pero se deja registrado como límite duro documentado por si el patrón de pruebas cambia (ej. pruebas de carga).
