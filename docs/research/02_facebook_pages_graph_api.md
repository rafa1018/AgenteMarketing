# Facebook Pages via Meta Graph API (publicación, comentarios, mensajes, insights, tokens)
Fecha de verificación: 2026-09-21 (verificación inicial 2026-09-18; re-confirmado el 2026-09-21 que la versión vigente sigue siendo v26.0 y que no hay nueva versión ni deprecación adicional publicada en developers.facebook.com/docs/graph-api/changelog entre ambas fechas)

> Método: todas las afirmaciones se contrastaron contra developers.facebook.com / facebook.com/business/help el 2026-09-18, con una segunda pasada de verificación el 2026-09-21 sobre los puntos más volátiles (versión vigente de la API y changelog). Las páginas de referencia de permisos y varias del Help Center se leyeron con navegador (el fetcher recibía HTTP 500 / páginas JS). Donde la documentación oficial no pudo confirmarse se escribe literalmente **NO VERIFICADO**. Cuando dos páginas oficiales se contradicen, se citan ambas.

## Resumen ejecutivo (5-10 viñetas con lo que más impacta el diseño)

- **Versión vigente: Graph API v26.0 (lanzada 2026-07-29).** Cada versión vive como mínimo 2 años; las llamadas sin versión usan la versión por defecto del App Dashboard (impredecible). Fijar la versión en una única constante de configuración (`META_GRAPH_VERSION=v26.0`) y planificar un upgrade anual.
- **Publicar en Páginas sí es posible (texto, link, foto, multi-foto, video, Reels) con Page access token + `pages_manage_posts` (+ `pages_read_engagement`, `pages_show_list`).** Publicar en perfiles personales NO es posible desde 2018 (`publish_actions` eliminado); la única alternativa es el Share Dialog manual.
- **Para uso propio/familiar NO se requiere App Review ni Business Verification**: en Standard Access la app puede pedir cualquier permiso a personas con rol en la app (admin/developer/tester) o con rol en el Business Portfolio conectado, incluso en modo Development. **PERO** los webhooks en modo Development solo llegan para acciones de personas con rol, y Messenger en Standard Access solo entrega mensajes de personas con rol. Atender a **clientes reales** (mensajes, y probablemente comentarios) exige app en Live + Advanced Access (App Review + Business Verification) al menos para `pages_messaging`.
- **Tokens para un sistema no supervisado: System User token del Business Portfolio** (sin expiración, o 60 días con `set_token_expires_in_60_days=true`, opción que Meta "recomienda" y dice que todas las integraciones deben adoptar). Alternativa: long-lived Page token (no tiene fecha de expiración pero se invalida al cambiar contraseña, perder rol, etc.). Usar siempre `appsecret_proof`.
- **No existe idempotencia nativa en Graph API para Pages** (solo Commerce Platform tiene `idempotency_key`). Facebook rechaza posts idénticos con error 506 "Duplicate Post", pero eso no sustituye una capa de idempotencia propia (publication_id + verificación previa + `GET /{post-id}` post-publicación).
- **Insights sufrió deprecaciones masivas (2024-03-14, 2025-06-15, 2025-11-15):** desaparecieron `page_engaged_users`, `page_consumptions`, `post_activity`, `page_fans*`, `page_impressions*`, `post_impressions*` y todas las variantes `*_unique`. Sustitutos: `page_media_view`, `post_media_view`, `page_total_media_view_unique`, `post_total_media_view_unique`, `page_follows`, `post_reactions_by_type_total`, `post_clicks`, `post_activity_by_action_type`. Además la referencia dice que Insights solo está disponible en Páginas con ≥100 likes, máximo 90 días por consulta y 2 años de histórico.
- **Webhooks:** callback HTTPS con certificado válido (no self-signed), verificación `hub.challenge`, firma `X-Hub-Signature-256` (HMAC-SHA256 con App Secret), reintentos con frecuencia decreciente durante 36 h → **deduplicación obligatoria** en n8n/PostgreSQL. Suscripción por página vía `POST /{page-id}/subscribed_apps` (`feed`, `mention`, `messages`, ...).
- **Rate limits:** con Page/System User token aplican Business Use Case limits (Pages: 4800 × usuarios interactuando / 24 h; header `X-Business-Use-Case-Usage` con `estimated_time_to_regain_access` en minutos; error 80001). Messenger: 200 × engaged users / 24 h y 300 llamadas/s por página. Reels: máximo 30 publicaciones por API / 24 h.
- **Messenger:** ventana estándar de 24 h; fuera de ella solo tags. `HUMAN_AGENT` (7 días) requiere App Review + Business Verification. Desde 2026-04-27 los tags `CONFIRMED_EVENT_UPDATE`, `ACCOUNT_UPDATE`, `POST_PURCHASE_UPDATE` devuelven error 100. Private replies a comentarios: 1 mensaje, dentro de 7 días, vía Send API con `recipient.comment_id`.
- **Multiempresa:** un solo Business Portfolio propio con un System User y las Páginas de las empresas familiares asignadas (propias o compartidas por partner) es viable según la documentación; que un System User publique en una página compartida por partner es coherente con las reglas del Help Center pero **NO VERIFICADO** con una prueba real: validar en Fase 6 antes de cerrar el diseño.

## Hechos verificados (cada viñeta termina con la URL fuente entre paréntesis)

**Versionado**
- La versión más reciente de Graph API es v26.0, lanzada el 29 de julio de 2026; v25.0 (18-feb-2026), v24.0 (8-oct-2025), v23.0 (29-may-2025), v22.0 (21-ene-2025), v21.0 (2-oct-2024), v20.0 (21-may-2024, disponible hasta septiembre/octubre de 2026 según la tabla). (https://developers.facebook.com/docs/graph-api/changelog)
- "Cada versión durará al menos 2 años a partir del lanzamiento"; al expirar una versión, las llamadas se redirigen a la versión anterior más antigua que siga funcionando; una llamada sin versión usa la versión configurada en el App Dashboard (Meta recomienda especificar siempre la versión). (https://developers.facebook.com/docs/graph-api/guides/versioning)

**Publicación en Páginas**
- Publicar texto/link: `POST /{page-id}/feed` con `message` y/o `link`; publicar foto: `POST /{page-id}/photos` con `url`; videos vía Video API. Publicación inmediata con `published=true` (default); programada con `published=false` + `scheduled_publish_time` (UNIX, ISO 8601 o string relativo tipo `strtotime`). La guía de Pages API indica que la fecha debe estar "entre 10 minutos y 30 días" desde la solicitud. (https://developers.facebook.com/docs/pages-api/posts)
- La referencia de `/{page-id}/feed` indica `scheduled_publish_time` entre 10 minutos y 75 días, `attached_media` como array `[{"media_fbid":"..."}]` con máximo 10 objetos, `backdated_time`, `call_to_action`, `targeting`/`feed_targeting`, `place`, `tags`, `multi_share_end_card`; respuesta `{"id":"post-id"}`; requiere Page token con tarea `CREATE_CONTENT` y permisos `pages_manage_posts`, `pages_read_engagement`, `pages_show_list`. Lectura: `limit` máx. 100 por petición, ~600 posts accesibles, filtrar publicados/no publicados con `is_published`. (https://developers.facebook.com/docs/graph-api/reference/page/feed/)
- `POST /{page-id}/photos`: `url` (foto alojada en Internet) o `source` (multipart/form-data), `caption`, `alt_text_custom`, `published`, `scheduled_publish_time` (solo Páginas), `temporary` (obligatorio cuando la foto se usará en un post programado), `no_story`. Formatos `.jpeg, .bmp, .png, .gif, .tiff`; "Los archivos no pueden superar los 4 MB" (PNG recomendado <1 MB). Devuelve `id` (photo) y `post_id`. Las fotos no publicadas se eliminan del servidor tras ~24 h. Requiere `pages_read_engagement`, `pages_manage_posts`, `pages_show_list` y tarea `CREATE_CONTENT`. (https://developers.facebook.com/docs/graph-api/reference/page/photos/)
- Campos del Page Post útiles para verificar: `id`, `permalink_url` ("URL estática permanente al post"), `is_published` (indica si un post programado ya se publicó), `created_time`, `scheduled_publish_time`, `message`, `status_type`, `full_picture`, `shares`, `is_hidden`, `promotable_id`; edges `reactions`, `comments`, `insights`, `attachments`. Se pueden actualizar `message`, `is_published`, `scheduled_publish_time`; `DELETE /{post-id}` soportado. Los posts expirados no se pueden leer. (https://developers.facebook.com/docs/graph-api/reference/pagepost/)
- Actualizar un post (`POST /{page-post-id}`) solo es posible para posts creados por la misma app. (https://developers.facebook.com/docs/pages-api/posts)
- Video en Página: `POST /{page-id}/videos` con `source` o `file_url` (no combinable con `upload_phase`), `title`, `description`, `published`, `scheduled_publish_time` (10 minutos a 6 meses), subida reanudable con `upload_phase` (start/transfer/finish/cancel), `upload_session_id`, `video_file_chunk`, `start_offset`, `file_size`. Permisos `pages_manage_posts`, `pages_read_engagement`, `pages_show_list`. (https://developers.facebook.com/docs/graph-api/reference/page/videos/)
- La Video API recomienda la Resumable Upload API: `POST /{app-id}/uploads` (nombre, tamaño, MIME) → `POST /upload:{upload-session-id}` con header `file_offset` y binario → `GET /upload:{upload-session-id}` para reanudar; el handle resultante se pasa a `POST /{page-id}/videos`. MIME aceptados: `video/mp4` (y `image/jpeg`, `image/png`, `application/pdf` para otros usos). El host `graph-video.facebook.com` está obsoleto; usar `graph.facebook.com`. (https://developers.facebook.com/docs/video-api/guides/publishing/ y https://developers.facebook.com/docs/video-api/overview/)
- Reels: 1) `POST /{page-id}/video_reels` con `upload_phase=start` → devuelve `video_id` y `upload_url`; 2) `POST rupload.facebook.com/video-upload/{version}/{video-id}` con headers `Authorization: OAuth {token}`, `offset`, `file_size` (o `file_url` para URL pública); 3) `POST /{page-id}/video_reels` con `upload_phase=finish`, `video_id`, `video_state=PUBLISHED|SCHEDULED|DRAFT`, `description`, `scheduled_publish_time`. Especificaciones: .mp4, 9:16, 1080×1920 (mín. 540×960), 3–90 s, 24–60 fps, H.264/H.265/VP9/AV1. Límite: 30 publicaciones vía API por 24 h. Permisos `pages_manage_posts`, `pages_read_engagement`, `pages_show_list`. (https://developers.facebook.com/docs/video-api/guides/reels-publishing)
- Idempotencia: el único `idempotency_key` documentado pertenece a Commerce Platform (órdenes/envíos/reembolsos), no a Pages. Batch requests (`POST /?batch=[...]`) admiten máximo 50 operaciones, no son atómicas y cada sub-llamada cuenta para el rate limit. (https://developers.facebook.com/docs/graph-api/batch-requests/)
- Error 506 "Duplicate Post": la recomendación oficial es "cambiar el contenido y reenviar". (https://developers.facebook.com/docs/graph-api/guides/error-handling)

**Permisos y niveles de acceso (referencia actualizada 5-dic-2025)**
- `pages_manage_posts`: crear, editar y eliminar publicaciones, fotos y videos de la Página; dependencias `pages_read_engagement`, `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_read_engagement`: leer contenido publicado por la Página (posts, fotos, videos, eventos), datos de seguidores (nombre y PSID), foto de perfil, metadatos y estadísticas de la Página; dependencia `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_read_user_content`: leer contenido generado por usuarios u otras Páginas en la Página (posts, comentarios, calificaciones), posts donde la Página está etiquetada, y eliminar comentarios de usuarios; dependencia `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_manage_engagement`: crear, editar y eliminar comentarios en posts de la Página y dar/quitar like como Página; dependencias `pages_read_user_content`, `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_manage_metadata`: suscribirse y recibir webhooks de actividad de la Página y actualizar sus ajustes; dependencia `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_messaging`: acceder y administrar conversaciones (y llamadas) de la Página en Messenger; uso permitido: experiencias iniciadas por el usuario, atención al cliente, confirmaciones de compras/reservas; dependencias `pages_manage_metadata`, `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `business_management`: leer y escribir con la Business Manager API (administrar activos como cuentas publicitarias); dependencias `pages_read_engagement`, `pages_show_list`. `read_insights`: leer estadísticas de Páginas, apps y dominios propiedad de la persona; dependencias `pages_read_engagement`, `pages_show_list`. (https://developers.facebook.com/docs/permissions/reference/)
- `pages_show_list`: listar las Páginas que administra el usuario. (https://developers.facebook.com/documentation/pages-api)
- Requisitos generales: "Revisión de apps de Meta: para apps que necesitan acceso a datos que no te pertenecen ni administras. Verificación del negocio: se requiere para todas las apps que solicitan Advanced Access." Puede exigirse una comprobación anual de uso de datos. Si la app no usa un permiso durante 90 días, el usuario debe volver a concederlo. (https://developers.facebook.com/docs/permissions/reference/)
- Standard Access: los permisos "solo se pueden solicitar a usuarios de la app que tengan un rol en la app solicitante"; se concede automáticamente a apps business/consumer/gaming. Advanced Access: cualquier usuario; exige Business Verification (obligatoria desde 2022-02-01), App Review por permiso y Data Use Checkup anual. (https://developers.facebook.com/docs/graph-api/overview/access-levels/)
- Modo Development: la app solo puede pedir permisos a "role users", con nivel Standard o Advanced, sin App Review. Modo Live: puede pedir permisos a cualquiera, pero solo los aprobados en App Review. (https://developers.facebook.com/docs/development/build-and-test/app-modes)
- Roles de app: Administrator, Developer y Tester "pueden conceder a la app cualquier permiso mientras está en desarrollo"; Analytics User no. Si la app está conectada a un Business Portfolio, los roles se gestionan en Business Manager; apps de negocios verificados admiten hasta 500 testers+analytics users, las no vinculadas ~50 testers. (https://developers.facebook.com/docs/development/build-and-test/app-roles)
- Business Verification: "Si tu app solo será usada por usuarios con rol en la propia app no necesitas completar la verificación; esos usuarios pueden conceder cualquier permiso en cualquier momento". Es obligatoria para Advanced Access y para apps que permiten a otras empresas acceder a sus datos. (https://developers.facebook.com/docs/development/release/business-verification)
- Pages API: "Todos los permisos y funciones relacionados con Páginas requieren aprobación mediante App Review antes de poder usarlos cuando la app pasa a Live"; en modo Development se pueden pedir a usuarios con rol sin esa aprobación. Tareas de Página: `MANAGE`, `CREATE_CONTENT`, `MODERATE`, `MESSAGING`, `ADVERTISE`, `ANALYZE` (+ `MANAGE_LEADS`, `VIEW_MONETIZATION_INSIGHTS`). (https://developers.facebook.com/docs/pages-api/overview)
- Tech Providers: empresas con necesidad legítima de acceder a datos de otras empresas; requieren Business Verification + Access Verification (independiente de App Review). Aplica cuando se accede a datos de negocios que no se poseen. (https://developers.facebook.com/docs/development/release/tech-providers/)
- Facebook Login for Business: solo para apps tipo Business; usa "configurations" (permisos, activos, tipo de token) definidas en el dashboard; dos tipos de token: User access token y Business Integration System User (BISU) token, este último "por defecto nunca expira", con opción de 60 días; la app debe estar asociada a un Business Portfolio propio y el cliente debe tener el suyo. (https://developers.facebook.com/docs/facebook-login/facebook-login-for-business)

**Tokens**
- Intercambio corto → largo: `GET /oauth/access_token?grant_type=fb_exchange_token&client_id={app-id}&client_secret={app-secret}&fb_exchange_token={short-lived}`; el token largo dura ~60 días; hacer la llamada desde servidor. Page token de larga duración: `GET /{user-id}/accounts` con user token largo. "Long-lived Page access token do not have an expiration date and only expire or are invalidated under certain conditions." (https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived y https://developers.facebook.com/documentation/facebook-login/guides/access-tokens/get-long-lived)
- Campo `access_token` del nodo Page: "solo se devuelve si el usuario que hace la petición tiene un rol (distinto de Live Contributor) en la Página. Puede requerirse autenticación en dos pasos para cuentas de negocio". (https://developers.facebook.com/docs/graph-api/reference/page/)
- Tipos de token: user, app, page, client; los Page tokens se obtienen intercambiando un user token vía `/{user-id}/accounts`. (https://developers.facebook.com/docs/facebook-login/guides/access-tokens)
- `GET /debug_token?input_token={token}&access_token={app-token|dev-user-token}` devuelve `app_id`, `application`, `type`, `expires_at`, `data_access_expires_at`, `is_valid`, `issued_at`, `scopes`, `granular_scopes`, `user_id`, `profile_id`. (https://developers.facebook.com/docs/graph-api/reference/debug_token/)
- Data access expiration: el acceso a datos expira a los 90 días de inactividad del usuario para la mayoría de permisos; excepciones que no expiran incluyen `ads_read`, `ads_management`, `business_management`, `pages_manage_posts`, `pages_messaging`, `read_insights`; se comprueba con `debug_token` y se renueva con `auth_type=reauthorize`. (https://developers.facebook.com/docs/facebook-login/auth-vs-data/)
- Errores de token: código 190 con subcódigos 458 (app no instalada), 460 (contraseña cambiada), 463 (expirado), 467 (inválido) → obtener nuevo token/re-autenticar. Códigos 4, 17, 341 (rate limit) → esperar y reintentar; 10 y 200-299 permisos; 368 acción abusiva; 506 duplicado. (https://developers.facebook.com/docs/graph-api/guides/error-handling)
- `appsecret_proof` = HMAC-SHA256(access_token, app_secret); activar "Require App Secret" en App Settings > Advanced > Security hace fallar cualquier llamada sin él. (https://developers.facebook.com/docs/graph-api/guides/secure-requests/)
- System Users: dos tipos, admin system user y system user (employee); representan servidores/software que ejecutan acciones programáticas sobre anuncios o Páginas. (https://developers.facebook.com/docs/marketing-api/system-users)
- El nivel de acceso de la app determina cuántos system users se pueden crear (Standard: 1 normal + 1 admin; Advanced: 10 + 1 según la tabla de la doc); "un system user solo puede tener rol en una app si ambos pertenecen al mismo negocio". (https://developers.facebook.com/docs/marketing-api/system-users/overview/)
- Crear: `POST /{business-id}/system_users` (`name`, `role=ADMIN|EMPLOYEE`); listar `GET /{business-id}/system_users`; no se pueden borrar, solo invalidar tokens. (https://developers.facebook.com/docs/marketing-api/system-users/create-retrieve-update)
- Instalar app y generar token: `POST /{system-user-id}/applications` (`business_app`); `POST /{system-user-id}/access_tokens` con `business_app`, `scope`, `appsecret_proof`, `set_token_expires_in_60_days=true`. Dos modalidades: sin expiración (asumir riesgo de fuga) o 60 días (recomendada); "todas las integraciones deben adoptar tokens con expiración". (https://developers.facebook.com/docs/marketing-api/system-users/install-apps-and-generate-tokens)
- UI Business Suite: Configuración → Usuarios → Usuarios del sistema → Agregar → asignar activos (páginas, cuentas publicitarias, catálogos) → Generar nuevo token → elegir app y permisos → el token se muestra una sola vez. Requiere una app asociada al portfolio; "No todas las empresas tienen acceso a los usuarios del sistema". (https://www.facebook.com/business/help/503306463479099 y https://www.facebook.com/business/help/327596604689624)
- Asignar Página a un usuario/system user vía API: `POST /{page-id}/assigned_users?user={id}&tasks=[MANAGE,CREATE_CONTENT,MODERATE,MESSAGING,ADVERTISE,ANALYZE]` con Page token de alguien con `MANAGE` y `pages_manage_metadata`; el edge lista "business and system users assigned to this page". (https://developers.facebook.com/docs/graph-api/reference/page/assigned_users/)
- Compartir Página con otro Business (partner/agencia): `POST /{page-id}/agencies` con `business` y `permitted_tasks`; requiere `MANAGE` y `business_management` (o `pages_manage_metadata` + `pages_show_list`). Las páginas recibidas como partner se listan en `GET /{business-id}/client_pages` con `permitted_tasks`. (https://developers.facebook.com/docs/graph-api/reference/page/agencies/ y https://developers.facebook.com/docs/graph-api/reference/business/client_pages/)
- Help Center: solo quien tiene control total del portfolio puede compartir con partners; el partner necesita su propio portfolio e ID; se puede dar control total o acceso parcial por tareas; "si le otorgas a un socio acceso parcial ... solo podrá asignar permisos a las personas de su portfolio comercial para que realicen las tareas específicas que le asignaste"; se pide activar 2FA en el portfolio. (https://www.facebook.com/business/help/1717412048538897)

**Webhooks**
- El callback debe aceptar HTTPS con certificado TLS válido (self-signed no soportado); verificación `GET` con `hub.mode=subscribe`, `hub.verify_token`, `hub.challenge` (devolver el challenge); notificaciones `POST` JSON con `object`, `entry[]`, `time`, `changes`; firma en header `X-Hub-Signature-256` con prefijo `sha256=` (HMAC-SHA256 con App Secret); responder `200 OK`; reintentos "inmediatos y luego con frecuencia decreciente durante 36 horas"; lotes de hasta 1000 updates no garantizados → deduplicar. (https://developers.facebook.com/docs/graph-api/webhooks/getting-started)
- "Apps in development mode only can receive test notifications initiated through the app dashboard or notifications initiated by people who have a role in the app." Webhooks no requiere App Review como producto, pero la app debe tener los permisos correspondientes. (https://developers.facebook.com/docs/graph-api/webhooks/)
- Campos de Página: `feed` ("casi todos los cambios del feed: posts, shares, likes, etc."), `mention`, `messages`, `messaging_postbacks`, `messaging_optins`, `message_deliveries`, `message_reads`, `message_reactions`, `message_echoes`, `messaging_referrals`, `ratings`, `live_videos`, `leadgen`, campos de perfil, etc. Payload `feed`: `value.item` (comment, post, reaction, share, status, photo, video, ...), `verb` (add, edit, edited, remove, hide, unhide, ...), `comment_id`, `post_id`, `parent_id`, `from{id,name}`, `message`, `reaction_type`, `created_time`, `published`/`is_published`, `permalink_url`. No se envían webhooks de anuncios (sí de comentarios en anuncios); notificaciones de likes de Página solo para <10K likes. Requiere `pages_manage_metadata` concedido por un admin con `MODERATE`. (https://developers.facebook.com/docs/graph-api/webhooks/reference/page/)
- `POST /{page-id}/subscribed_apps?subscribed_fields=feed,mention,messages` con Page token (`CREATE_CONTENT`, `MANAGE` o `MODERATE`) + `pages_manage_metadata` + `pages_show_list`; `GET` lista suscripciones; `DELETE` con app token; no sirve para Instagram (se configura en el dashboard). (https://developers.facebook.com/docs/graph-api/reference/page/subscribed_apps/)
- Messenger webhooks: "Standard Access para recibir notificaciones de personas con rol en la app (admins, developers, testers); Advanced Access para recibir notificaciones de tus clientes"; responder 200 en ≤5 s; firma SHA256 recomendada. (https://developers.facebook.com/docs/messenger-platform/webhooks)

**Comentarios y Messenger**
- `GET /{object-id}/comments` con `filter=toplevel|stream`, `summary=true` (`order`, `total_count`); `POST /{object-id}/comments` con `message` | `attachment_url` | `attachment_id` requiere `pages_manage_engagement` y Page token con `MODERATE`; los comentarios de objetos de Página devuelven vacío con user token. (https://developers.facebook.com/docs/graph-api/reference/object/comments/)
- Campos de Comment: `id`, `message`, `from`, `created_time`, `is_hidden`, `can_hide`, `can_reply_privately`, `can_comment`, `parent`, `permalink_url`, `attachment`; ocultar: `POST /{comment-id}?is_hidden=true`; eliminar: `DELETE /{comment-id}`; permisos `pages_manage_engagement`, `pages_read_user_content` (y `pages_manage_metadata` en algunos casos); errores 200, 368, 190. (https://developers.facebook.com/docs/graph-api/reference/comment/)
- Reacciones: `GET /{post-id}/reactions?summary=total_count` (tipos LIKE, LOVE, WOW, HAHA, SAD, ANGRY, CARE, ...). (https://developers.facebook.com/docs/graph-api/reference/post/reactions/)
- Private replies: `POST /{page-id}/messages` con `recipient.comment_id` o `recipient.post_id`; "dentro de 7 días desde la creación del post o comentario"; "solo se puede enviar un mensaje" (la conversación continúa si el usuario responde en 24 h); requiere `pages_messaging` y tarea `MESSAGING`; no se puede enviar a otra Página; "Standard Access apps can only access data for people who have a role on the app". (https://developers.facebook.com/docs/messenger-platform/discovery/private-replies)

## Lo que NO es posible / limitaciones duras

- **Publicar en perfiles personales (timeline de usuario) vía API**: eliminado desde 2018-04-24/2018-08-01 (`publish_actions`). Solo queda el Share Dialog, que requiere acción manual del usuario en el navegador; no automatizable.
- **Publicar sin Page access token** (o System User token con la Página asignada): no existe modo "app-only" para publicar.
- **Recibir webhooks de personas sin rol mientras la app está en modo Development**: la documentación general de Webhooks lo excluye explícitamente; Messenger exige Advanced Access para mensajes de clientes.
- **Enviar mensajes de Messenger a un cliente fuera de la ventana de 24 h** sin un tag válido: solo `HUMAN_AGENT` (7 días; requiere App Review + Business Verification) y `CUSTOMER_FEEDBACK`; los otros tres tags devuelven error 100 desde 2026-04-27. No hay envío proactivo a PSIDs que nunca escribieron a la Página (salvo Sponsored Messages, pago).
- **Private reply a un comentario después de 7 días o más de una vez**: no permitido; tampoco hacia otras Páginas.
- **Idempotencia nativa**: no existe `idempotency_key` para Pages. El 506 "Duplicate Post" solo bloquea contenido idéntico reciente y no es una garantía.
- **Insights en Páginas pequeñas**: la referencia oficial dice que Page Insights solo está disponible en Páginas con ≥100 likes (ver "Puntos NO verificados": comportamiento real en 2026). Máximo 90 días por consulta y 2 años de histórico.
- **Métricas eliminadas**: `page_engaged_users`, `page_consumptions`, `post_activity`, `page_fans*`, `page_impressions*`, `post_impressions*`, `*_impressions_unique*`, `post_video_views_unique`, `page_video_views_unique` → devuelven "invalid metric". `post_engaged_users` no aparece en la referencia v26.0.
- **Editar posts creados por otra app o desde Business Suite** vía `POST /{post-id}`: solo se pueden actualizar posts creados por la misma app.
- **Reels**: máximo 30 publicaciones por API cada 24 h; duración 3–90 s; formato 9:16. **Fotos**: máximo 4 MB. **Multi-foto**: máximo 10 `attached_media`.
- **Programación**: `scheduled_publish_time` mínimo 10 minutos; máximo 30 días (guía Pages API) o 75 días (referencia `/feed`); videos hasta 6 meses. Diseñar con el límite más conservador (30 días) hasta probarlo.
- **Lectura de `/feed`**: `limit` ≤100 y aprox. 600 posts accesibles; los posts expirados no se pueden leer.
- **System users**: número limitado por nivel de acceso de la app; solo pueden tener rol en apps del mismo Business; no se pueden borrar (solo invalidar tokens); "no todas las empresas tienen acceso a los usuarios del sistema".
- **Compartir una Página con un tercero**: solo el propietario con control total del portfolio puede compartirla; un partner con acceso parcial no puede re-compartirla.
- **Webhooks de Instagram** no se suscriben con `subscribed_apps`; solo desde el dashboard (tema de otro documento).
- **Use cases** no se pueden quitar de una app una vez añadidos.

## Requisitos previos (cuentas, roles, permisos, verificaciones, modo desarrollo vs producción)

1. **Cuenta de desarrollador de Meta** registrada (developers.facebook.com) con la cuenta personal de Facebook del dueño del proyecto.
2. **Business Portfolio (Business Manager) propio** del dueño del proyecto. Es donde vivirá la app, el System User y las Páginas asignadas. Activar autenticación en dos pasos en el portfolio (el Help Center lo pide antes de compartir activos con partners y la referencia del nodo Page indica que puede exigirse 2FA para obtener `access_token` en cuentas de negocio).
3. **Páginas**: cada empresa familiar debe tener su Página de Facebook (Nueva experiencia de Páginas) con el dueño del proyecto como admin con tareas `MANAGE`/`CREATE_CONTENT`/`MODERATE`/`MESSAGING`/`ANALYZE`, o bien la Página debe estar en el portfolio propio (owned) o compartida como partner (client page) con esas tareas.
4. **App tipo Business** creada con el use case "Manage everything on your Page" (añade `business_management`, `pages_show_list`, `public_profile`); añadir después los permisos `pages_manage_posts`, `pages_read_engagement`, `pages_read_user_content`, `pages_manage_engagement`, `pages_manage_metadata`, `pages_messaging`, `read_insights`. Añadir productos Webhooks y, cuando toque, use cases de Instagram/WhatsApp/Marketing API (no se pueden quitar después: añadir solo lo necesario). No marcar la opción Tech Provider (no se accede a datos de otros negocios: todos los activos estarán en/compartidos con el portfolio propio).
5. **Configuración de la app**: App Secret guardado en `.env`; activar "Require App Secret"; Privacy Policy URL, Data Deletion URL e icono son obligatorios solo para pasar a Live.
6. **Modo Development (Fases 3-6)**: suficiente para publicar, programar, leer posts, comentarios propios/de personas con rol, insights, y probar webhooks con usuarios con rol. Los permisos se conceden con Standard Access sin App Review ni Business Verification porque todos los usuarios (el dueño y sus familiares administradores) tienen rol en la app o en el Business Portfolio.
7. **Modo Live + Advanced Access (Fase 8, Customer Agent con clientes reales)**: requiere Business Verification del portfolio, App Review (video/screencast del flujo para cada permiso) al menos para `pages_messaging` (documentado) y previsiblemente para `pages_read_user_content`/`pages_manage_engagement`/`pages_manage_metadata` (ver NO verificados), y Human Agent feature si se quiere responder después de 24 h. Data Use Checkup anual.
8. **System User** (recomendado): crear en Business Suite → Usuarios del sistema (rol Employee para operar, Admin solo para administración), asignar Páginas (y luego IG/ad accounts), instalar la app, generar token con los scopes anteriores; elegir expiración 60 días con rotación automatizada o sin expiración si se acepta el riesgo. Almacenar en `.env`/credenciales de n8n; nunca en workflows.

## Webhooks (eventos, requisitos de URL, verificación, firma, deduplicación, comportamiento en modo desarrollo)

- **Objeto `page`, campos relevantes**: `feed` (comentarios: `item=comment`, `verb=add|edited|remove|hide|unhide`, con `comment_id`, `post_id`, `parent_id`, `from{id,name}`, `message`, `created_time`; reacciones: `item=reaction`, `reaction_type`; posts/shares/status/photo/video), `mention`, `messages`, `messaging_postbacks`, `message_reactions`, `message_reads`, `message_deliveries`, `message_echoes`, `messaging_referrals`, `leadgen` (futuro Ads), `ratings` (webhooks de ratings dejaron de enviarse en v22.0).
- **Requisitos de URL**: endpoint público HTTPS con certificado válido (Let's Encrypt/Cloudflare sirve; self-signed no). En local se necesita un túnel (p. ej. Cloudflare Tunnel) hacia el webhook de n8n; en VPS, dominio + TLS. Dos rutas en n8n: la misma URL debe responder al `GET` de verificación y a los `POST` de eventos.
- **Verificación**: `GET ?hub.mode=subscribe&hub.verify_token=...&hub.challenge=...` → comparar `hub.verify_token` con `META_WEBHOOK_VERIFY_TOKEN` y devolver `hub.challenge` en texto plano con 200.
- **Firma**: header `X-Hub-Signature-256: sha256=<hex>`; calcular HMAC-SHA256 del cuerpo crudo (raw body, sin re-serializar) con `META_APP_SECRET` y comparar en tiempo constante; rechazar (pero responder 200 o 401 sin procesar) si no coincide. Configurar el nodo Webhook de n8n para exponer el raw body.
- **Respuesta**: 200 OK rápido (Messenger: ≤5 s). Procesar de forma asíncrona (encolar en PostgreSQL y devolver 200 de inmediato; el trabajo pesado en otro workflow).
- **Reintentos / duplicados**: Meta reintenta inmediatamente y luego con frecuencia decreciente hasta 36 h si no recibe 200; puede agrupar hasta 1000 cambios por `POST`; no hay ID de entrega único garantizado → **deduplicar por clave de negocio**: `(object, entry.id, item, verb, comment_id|post_id|mid, created_time)` con índice único en `marketing_events`/`inbound_events`. Los `message.mid` de Messenger sirven como clave natural.
- **Suscripción**: 1) configurar el producto Webhooks en el App Dashboard (Callback URL + Verify Token, objeto Page, campos); 2) por cada Página `POST /{page-id}/subscribed_apps?subscribed_fields=feed,mention,messages,...` con Page token con `pages_manage_metadata`. Repetir para cada nueva empresa (10_COMPANY_Management).
- **Modo Development**: "Apps in development mode only can receive test notifications initiated through the app dashboard or notifications initiated by people who have a role in the app." Las publicaciones, comentarios y mensajes hechos por el propio dueño/familiares con rol sí generan webhooks (útil para probar en Fases 6-8). Comentarios/mensajes de clientes reales sin rol: no llegan en Development; en Messenger requieren Advanced Access (App Review); para `feed` en Live + Standard Access el comportamiento exacto es NO VERIFICADO (ver abajo).
- **mTLS**: opcional (documentado para WhatsApp); la CA de los webhooks cambió el 2026-03-31 (changelog v25.0): si se valida el certificado cliente de Meta, actualizar la CA.

## Límites, cuotas y costos

- **Costos**: Graph API, Pages API, Webhooks y Messenger Platform no tienen costo por llamada ni por mensaje (los costos aparecen solo en Ads, Sponsored Messages y en WhatsApp, fuera de este documento). NO VERIFICADO literalmente en una página de precios (Meta no publica una tabla de precios para Pages API), pero ninguna doc consultada menciona tarifas.
- **Rate limits por tipo de token**: user/app token → Platform limits (200 llamadas/hora × usuarios; `X-App-Usage`); Page/System User token → Business Use Case limits: Pages = 4800 × usuarios que interactuaron con la Página en 24 h; `X-Business-Use-Case-Usage` incluye `estimated_time_to_regain_access` (minutos); error 80001 "too many calls to this Page account". Error 32 en Platform limits de Páginas. El throttling empieza al llegar al 100 % de `call_count`, `total_cputime` o `total_time`.
- **Messenger**: 200 × engaged users / 24 h; 300 llamadas/s por Página (texto) y 10/s (audio/video); error 80006.
- **Publicación**: Reels ≤30 por API/24 h; fotos ≤4 MB; `attached_media` ≤10; `scheduled_publish_time` 10 min–30/75 días (video 6 meses); fotos no publicadas expiran a las ~24 h.
- **Lectura**: `/feed` `limit` ≤100 y ~600 posts; Insights ≤90 días por consulta, 2 años de histórico, actualización cada 24 h, Páginas ≥100 likes.
- **Batch**: ≤50 operaciones; cada una cuenta para el rate limit.

### Evidencia

- **Modelo OWNER/AGENCY y System Users citados explícitamente como titulares de acceso "a través de un negocio":** "Si el token de acceso que se utilizó para realizar la llamada a la API pertenece a un usuario o a **un usuario del sistema** que posee acceso al activo solicitado a través de un negocio, el acceso al activo solo se puede conceder si el negocio es el OWNER del activo en cuestión. No puedes conceder acceso a activos en los que solo figuras como AGENCY." — esto confirma (a) que un System User puede tener acceso a un activo por la vía AGENCY (no solo OWNER), y (b) que ese acceso AGENCY no se puede volver a compartir con un tercero (coincide con lo ya escrito en este archivo sobre partners con acceso parcial). (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/business-to-business)
- **Compartir sin ceder propiedad, para Página, cuenta publicitaria e Instagram por igual:** el mismo documento muestra tres llamadas equivalentes que un negocio ya conocido por el propietario puede usar para pedir acceso AGENCY sin tomar posesión: `POST /{page-id}/agencies` con `permitted_tasks=['MODERATE','ADVERTISE','ANALYZE']`, `POST /{business-id}/client_ad_accounts` con `permitted_tasks=['ADVERTISE','ANALYZE']`, y `POST /{business-id}/client_pages` con `permitted_tasks=['ADVERTISE','ANALYZE']`. Nótese que este ejemplo sí incluye `MODERATE` para una Página vía `page/agencies`, lo que sugiere que moderar comentarios ajenos sí es alcanzable por esta vía (a diferencia de lo que sugiere la guía de "Páginas" citada abajo). (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/business-to-business)
- **Activos "propios o compartidos" en Business Asset Groups, para los tres tipos de activo de la pregunta:** "Los grupos de activos comerciales pueden contener cuentas publicitarias, páginas, píxeles de Facebook, conjuntos de eventos offline, apps, catálogos, conversiones personalizadas y cuentas de Instagram. Los activos pueden ser propiedad de un negocio **o compartidos para proporcionar acceso a una agencia**." Y en la guía de "Administrar activos": "Puedes agregar páginas propias o compartidas"; "Los grupos de activos comerciales pueden incluir cuentas publicitarias propias o compartidas"; "Puedes agregar cuentas compartidas o propias de Instagram". (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/asset-groups y https://developers.facebook.com/docs/marketing-api/business-asset-management/guides/assets)
- **Restricción específica de Páginas — el `business` de `assigned_users` debe ser el propietario:** en la guía "Páginas", justo antes del ejemplo de `POST /{page-id}/assigned_users?user=BUSINESS_SCOPED_USER_ID&tasks=[...]&business=BUSINESS_ID`, el texto dice literalmente: **"El identificador de la empresa debe ser el identificador del negocio que posee la página."** Esto es nuevo respecto a lo escrito antes en este archivo (que citaba `page/assigned_users` sin esa condición) y sugiere que un System User del negocio AGENCY (el dueño) no puede recibir tareas `CREATE_CONTENT`/`MODERATE`/`MESSAGING`/`MANAGE` en la Página del familiar por esta vía; solo el negocio propietario puede asignar esas tareas con `assigned_users`. (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/pages)
- **La misma guía de Páginas enmarca el acceso AGENCY como orientado a anuncios:** "Reclamar páginas como agencia... **La agencia puede empezar a publicar anuncios en la página (a través de cuentas publicitarias a las que tiene acceso) de manera inmediata.**" y "**La agencia no puede volver a compartir la página con otro negocio.**" El ejemplo de `client_pages` para una Página ajena usa `permitted_tasks=['ADVERTISE','ANALYZE']`, sin `CREATE_CONTENT` ni `MESSAGING`. (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/pages)
- **Cuentas publicitarias: mismo mecanismo OWNER/AGENCY, sin la restricción de "solo el propietario puede usar `assigned_users`":** "`access_type` define si el negocio actúa como OWNER o AGENCY de la cuenta publicitaria." y "Cuando el administrador comercial esté asociado a una cuenta publicitaria, podrás asignar tareas a otros usuarios del negocio" (`POST /act_<AD_ACCOUNT_ID>/assigned_users` con `user=BUSINESS_SCOPED_USER_ID` y tareas `MANAGE`/`ADVERTISE`/`ANALYZE`), sin exigir que el negocio sea el propietario de la cuenta. Para solicitar ese acceso: "Para solicitar el acceso a activos que pertenecen a otros administradores comerciales, consulta las funciones de empresa a empresa." (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/ad-accounts)
- **Cuentas de Instagram: el negocio del dueño puede ser "agencia" de una cuenta de Instagram del familiar y asignar tareas de contenido/mensajes/anuncios a sus propios usuarios:** "Para ver todas las cuentas de Instagram de las que tu negocio es una agencia, usa esta llamada GET: `GET /{business-id}/client_instagram_assets`... Esta acción devuelve una lista de cuentas de Instagram que les pertenecen a **clientes** de un portfolio comercial." Las tareas asignables vía `POST /<INSTAGRAM_BUSINESS_ASSET_ID>/assigned_users` incluyen `CONTENT` ("Crear, administrar o eliminar publicaciones, historias y más en nombre de la cuenta de Instagram"), `MESSAGES`, `COMMUNITY_ACTIVITY`, `ADVERTISE`, `ANALYZE`; no se repite aquí la frase "el negocio debe ser el propietario" que sí aparece en la guía de Páginas. (https://developers.facebook.com/docs/business-management-apis/business-asset-management/guides/instagram-accounts)
- **Contexto ya existente en este archivo, sin cambios:** `POST /{page-id}/assigned_users` (referencia clásica de Graph API) acepta "Business user id or system user id" sin mencionar la restricción de negocio propietario; `POST /{page-id}/subscribed_apps` exige un Page token con tarea `CREATE_CONTENT`, `MANAGE` o `MODERATE` + `pages_manage_metadata` (ver secciones "Tokens" y "Webhooks" de este mismo archivo). (https://developers.facebook.com/docs/graph-api/reference/page/assigned_users/ y https://developers.facebook.com/docs/graph-api/reference/page/subscribed_apps/)

### Contradicción explícita frente a lo ya escrito en este archivo

Este archivo decía (resumen ejecutivo y "Puntos NO verificados"): *"que un System User publique en una página compartida por partner es coherente con las reglas del Help Center pero NO VERIFICADO... no hay una frase oficial explícita sobre system users en client pages."* La investigación de esta ampliación matiza eso en dos direcciones:

1. **Refuerza** la parte de que un System User puede tener acceso "a través de un negocio" en modo AGENCY (frase oficial explícita nueva, ver evidencia arriba) — esto ya no es solo inferencia del Help Center, es texto literal de developers.facebook.com.
2. **Contradice/reduce el alcance** de la conclusión implícita de que ese acceso cubre publicación orgánica, moderación y webhooks igual que en una Página propia: la guía nueva de "Páginas" en Business Asset Management sugiere que, para tareas de contenido (`CREATE_CONTENT`), moderación (`MODERATE`) y mensajería (`MESSAGING`) asignadas vía `assigned_users`, el negocio debe ser el **propietario**, y el flujo AGENCY documentado para Páginas está enmarcado explícitamente para anuncios. Esta restricción, en cambio, **no aparece** en las guías equivalentes de cuentas publicitarias ni de cuentas de Instagram, donde el modelo AGENCY sí permite asignar tareas de contenido/mensajería a los propios usuarios (incluyendo, por extensión razonable, System Users) sin exigir propiedad.

### Implicación para el diseño

- **Cuentas de Instagram y cuentas publicitarias:** el modelo de una sola tabla `company_social_accounts` con un único System User del portfolio del dueño parece viable según la documentación oficial encontrada: el familiar comparte la cuenta de Instagram o la cuenta publicitaria como "cliente" (AGENCY) del portfolio del dueño (`client_instagram_assets` / `client_ad_accounts`), sin ceder la propiedad, y el System User del dueño puede recibir tareas `CONTENT`/`MESSAGES`/`ADVERTISE`/`ANALYZE` (Instagram) o `MANAGE`/`ADVERTISE`/`ANALYZE` (cuenta publicitaria) vía `assigned_users` sobre ese activo compartido.
- **Páginas de Facebook (el caso más usado hoy: publicar posts, leer/moderar comentarios, Messenger, webhooks `feed`/`messages`):** el diseño **no debería asumir** que basta con que el familiar comparta la Página como AGENCY del portfolio del dueño para que el System User del dueño publique contenido orgánico, modere comentarios o reciba webhooks. La ruta documentada con más respaldo para esas tareas específicas es que el familiar dé al **negocio propietario** (o directamente al System User, si `assigned_users` en la práctica permite pasar un `business` distinto del propietario cuando quien llama tiene el rol adecuado — esto no quedó claro y es NO VERIFICADO) los roles de Administrador/Editor/Moderador sobre la Página. Antes de cerrar el modelo de datos, **hay que probarlo en Fase 6** con una Página real de un familiar: (a) compartirla como partner (AGENCY) al portfolio del dueño con `permitted_tasks` amplios (`MANAGE, CREATE_CONTENT, MODERATE, MESSAGING, ADVERTISE, ANALYZE`) vía `POST /{page-id}/agencies`, (b) intentar `POST /{page-id}/assigned_users` para asignar el System User del dueño con esas tareas, y (c) si falla, probar `POST /{page-id}/subscribed_apps` y `POST /{page-id}/feed` directamente con el Page token obtenido tras el paso (a) para ver si el `permitted_tasks` de la relación AGENCY ya habilita esas llamadas sin pasar por `assigned_users`.
- Si la prueba de Fase 6 confirma que Páginas **sí** requieren ceder la propiedad (u otorgar rol de Administrador de Página directamente, fuera del modelo de portfolio) para publicar/moderar/recibir webhooks, el requisito "agregar nuevas empresas sin rediseñar todo" se mantiene igual (el onboarding de cada empresa nueva simplemente incluiría un paso adicional: "el familiar te agrega como Administrador/Editor de la Página" en vez de solo "comparte la Página con el portfolio"), por lo que **no obliga a rediseñar el modelo de datos** `company_social_accounts` de una sola tabla; solo cambia el procedimiento de onboarding documentado en 10_COMPANY_Management, no la estructura de credenciales.
